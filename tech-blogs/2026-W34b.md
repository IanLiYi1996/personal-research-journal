### ⭐⭐⭐ 而这推翻了「每天一跑」这条规矩的**理由**（结论不变，理由换了且更强）

CLAUDE.md 里我给 tech-blogs 每天一跑的依据一直是**产出率**：`3h→1 篇 / 9h→33 / 28h→65 / 40h→82`，据此说「每天一跑是对的、一天多次无价值」。

⭐⭐⭐ **但那个论证回答的是「多跑一次值不值」，它回答不了「能不能跳过一天」——而我此前把两者当成一件事了。** 本次测量给出后者的独立答案：

> ⭐⭐ **不能跳过一天，不是因为会积压，而是因为最浅的那几个 feed 深度不足一天 ⟹ 跳一天就是永久丢失。**

⚠️ **同时给出一条我不打算现在做的动作**：真正的对策不是改窗口，而是 (a) 保证运行频率 ≥ 最浅 feed 的深度（已满足，若 cron 不静默停跑）或 (b) **把每次原始抓取落盘，使「跳过一天」在事后可检测**——后者正是我 08-15~17 那次缺口的根本对策（心跳产物），仍待定。

## §1 ⭐⭐⭐ Deep dive：Databricks 的 Grounded Reasoning Cup —— 一场**把模型控住、只让 harness 变**的现场竞赛

**[Evaluating AI Agents Live at the Grounded Reasoning Cup](https://www.databricks.com/blog/evaluating-ai-agents-live-grounded-reasoning-cup)**（Databricks AI Research Team）

### 赛制（值得逐条记，因为几个设计恰好是我这两周攒的对策）

| 项 | 内容 |
|---|---|
| 参赛 | **11 支北美高校队**，每队 2–4 人 |
| ⭐⭐⭐ **模型约束** | 每队配一个 frontier lab 伙伴（**OpenAI / Anthropic / Google DeepMind**），提供模型与指导，**唯一硬约束是必须专用该 lab 的模型家族** |
| 开发期 | 约 2 个月，在公开的 **OfficeQA** 基准上迭代 |
| ⭐⭐⭐ **比赛当天** | 换到全新发布的 **OfficeQA Pro V2**（约 **12 万页美国财政部文档**） |
| ⭐⭐⭐ **防过拟合** | 新语料（U.S. Treasury 的 Accounts of Receipts and Expenditures）**在开赛前仅 36 小时释出**——够处理与建索引，不够让方法过拟合 |
| 自由度 | agent 框架 / 语料版本 / 检索策略 / 工具设置 / **human-in-the-loop 皆可** |

⭐⭐⭐ **「新语料只提前 36 小时释出」是我追的那条防作弊设计的第三个变体**：Gaming Without an Attacker 是「探针只在**未披露且不可枚举**的轴上有效」、ProMax 是「只挖**训练截止日之后**的 commit」，**本篇是「把暴露窗口压到 36 小时」**——三者都在解决「被测者是否见过答案」，但用的资源不同（未披露 / 时间下界 / 时间窗宽度）。

### 结果

| | 准确率 |
|---|---:|
| **Stanford（冠军）** | **63.3%** |
| 前三名（Yale / UMass / Stanford）| 均 >50% |

⭐⭐⭐ **本篇最该记的一个数字（也是我唯一敢当 harness 效应引用的那个）：**

> **「The average gap between the top scoring and lowest scoring teams using the same model was 30.4 points.」**

⟹ ⭐⭐⭐ **同一个模型、11 支独立队伍、现场条件下，最高分与最低分相差 30.4 个百分点。这是 harness 效应的第七次独立实证，也是目前最接近「田野实验」的一次**（此前六次：LongHorizon-Harness 的 Qwen+新 harness > Opus+原生 CC / Evo-Bench 29.7→46.3 / ProMax 的 mini-swe-agent 21.8%→OpenHands 41.2% / A²E 的 9 harness × 23 benchmark 同骨干 / AI4AI 的 57 次均值 +0.275 且 100% 超基线 / OpenART 的「运行时实现解释相当一部分安全差异」）。

⭐ **它的独特之处在于「谁来做 harness」**：前六次的对照都是**研究者自己或自动搜索**生成若干 harness，本次是**11 组互不通气的人类团队各自独立设计**——⟹ **30.4 分不是某个搜索空间的跨度，而是「一个有能力的团队在两个月里能把同一个模型的表现拉开多远」的经验分布宽度。** 这个量对客户沟通比任何自动化实验都直接。

### ⚠️⚠️ 而作者主动标出一处不可比，这也是我**不**引用「+35 分」那个数字的原因

原文：

> **「One caveat is that the offline setting that baselines were run in is not directly comparable with the competition setting teams were tasked with. In our offline agent evaluations, a frozen agent configuration is run once across the full test set, with no round structure, no pauses, and no chance to react to intermediate failures.」**

⟹ ⭐⭐ **「冠军比 frontier agent 离线基线高约 35 分」里混进了一个巨大的自由度差：队伍能在轮间观察失败并调整，基线是冻结配置跑一遍。所以那 35 分不能读成 harness 效应，而 30.4 分（同模型、同赛制）可以。**⭐ **值得表扬的披露**：这类「我们自己的对照不可比」通常是我得自己挖出来的，本篇写在了图注里。

### ⭐⭐⭐ 三支队伍各是我一条主线的实现，其中冠军那条是**负面结果**

**1st Stanford —— 把失败模式编成技能库，然后为了速度把验证器关掉**

- 开发期反复把错误答案**追回到 agent 具体走错的那一步**，再把该模式变成技能（表格定位 / 答案格式化 / 常见金融措辞澄清…），⭐ 还包括「何时搜已解析文本与 markdown 表示、何时回退到源 PDF」的判断技能
- 到比赛日备了 **100+ 条技能的 playbook**，驱动 **Claude Opus 4.8 的 Claude Code agent**（开发期消融里用过 Opus 4.8 与 **Fable 5（"while available"）**）
- 尝试 88 题答对 **57** 题，准确率全场第一
- ⭐⭐⭐ **前三轮用另一个 Claude Code agent 当 verifier**（重抽中间值、查常见失效如「沿数据血缘追修订值」与单位缩放、发现不一致就补算）；**但前三轮只拿到 2 个速度奖，于是后三轮把这道验证整个撤掉**，延迟大降、速度奖拿到 14 个，靠这个反超；**末轮又把它开回来，用最后一次重交改对一个答案，锁定冠军**

⟹ ⭐⭐⭐ **这是我第一次看到「验证」被放在一个明确的计分规则下与延迟做交换，而最优策略既不是常开也不是常关，是「选择性开启」。** 而它给我一个此前缺的**机制解释**：

> AI4AI 曾测出**验证类技术是自动演化最少长出来的**（verification/arbiter 12%、self-consistency 5%，而 format enforcement 100%），Evo-Bench 也观察到演化出的 harness「verifier 完全放行」。我当时的结论是「若验证最不容易长出来，它就该是人工优先固定的部分」——**但那只是观察，没有原因。**
>
> ⭐⭐⭐ **Stanford 的行为给出原因：验证的成本落在每一道题上，收益只落在少数几道题上。所以在一个把延迟计进分数的目标下，撤掉验证是理性的——那么一个优化含延迟目标的自动搜索也会撤掉它。**
>
> ⟹ ⭐⭐ **对「证据面」（Runtime Contract 那条主线）的直接含义：想让证据闸门留在生产里，计分规则就不能把闸门的成本记在与吞吐同一个预算上。** 否则不需要任何人作恶，闸门会被合理地优化掉。

**2nd UMass —— 速度押注，差 1.75 分**

- 主力 **Claude Opus 4.8 Fast**，预处理语料建**元数据目录**以支持快速检索过滤；**每题并行跑 3 个 agent，最后一次 Opus 调用选最好的答案**
- 正确答案的平均提交时间 **4 分钟**，全场平均是 **8 分 30 秒**（不到一半）；⭐ **拿到 36 个速度奖，是 Stanford（16 个）的两倍多**
- **中场领先 Stanford 10.25 分**，进末轮仍领先 3.75 分，**一直领先到比赛最后 56 秒**，被 Stanford 更慢更准的 agent 在最难的题上反超，**最终差 1.75 分**

⟹ ⭐⭐ **不能把这读成「准确率胜过速度」：速度差一点就赢了，而决定胜负的是「末轮双倍」这条计分规则。**⭐ 我记这条是因为这类结果极易被总结成一句普适结论，而它实际高度依赖赛制权重。

**3rd Yale —— 「多个独立视角的交集」的一个完整实现，且聚合器被**限制只能选择不能生成****

- 四条并行 arm 跨两种 agentic 策略：2 条自主 **ReAct**（分别由 **Gemini 3.1 Pro** 与 **Gemini 3.5 Flash** 驱动）+ 2 条更结构化的 **planner–verifier** 流水线（全部 LLM 调用用 Gemini 3.1 Pro）；planner 先勘察并语境化源文档、攒出含证据的 scratchpad，verifier 再核引用并做最终计算
- **Gemini 3.1 Pro 的 meta-verifier** 审阅四条 arm 的答案与推理并选最终答案；⭐⭐⭐ **为降低引入新的无支撑答案的风险，meta-verifier 只能在已有 arm 提出的答案里选**；选不出来则退到多数投票
- 自陈动机是「**independent, partially decorrelated failure modes**」；90 题答对 49 题，六轮里四轮进正确率前三

⟹ ⭐⭐⭐ **「聚合器只许在独立生成的候选上做选择、不许生成」正是我从 U-OPSD vs Gaming 归纳出的那条区分的工程实现**（多条独立 rollout 的一致性稳健 vs 单一可优化标量腐化），⭐ **也与 DarwinX 的「只生成对强基线的有界修改」是同一个设计手法——限制那一步的搜索空间。**⭐⭐ 而「刻意让失效模式部分去相关」正是 Anthropic 多 agent 那篇「低方差 → 同质群体的系统性失效」的正面版本：一篇讲同质的代价、一篇讲多样的收益、本篇是把它做进比赛系统。

### 作者自己归纳的五条设计杠杆（可直接当检查表）

1. **预解析文档**并加元数据（图表描述、页级元数据），⭐ **且保留回到源 PDF 的路径**以在解析不全时回退
2. **不用通用 top-k chunk 检索**，改用某种词法检索（如 `grep`）常配稠密检索做混合
3. 把搜索 / 文档勘察 / 计算 / 比较 / 提交**委派给专门工具**
4. 显式的**验证检查**（验证 agent 或 LLM 调用）
5. ⭐ **现场压力下，预处理 / 重试逻辑 / 并行 / 提交 scaffolding 这类运维细节决定正确答案能不能按时交上去**

⭐ 第 5 条少见但很实在：**它说的是「答对了但没交上」也是一种失效**，而这不属于任何模型能力维度。

### ⚠️ 保留（必须一起说）

- ⭐⭐ **Databricks 同时是主办方、基准所有者（OfficeQA）与产品卖方（Genie）**。文中用比赛结论导向产品：「pre-parsing documents with [Genie] contributes significantly to Genie's performance improvement of **24.0 pt** over baseline frontier agents」⟹ **队伍的成绩是第三方产出，产品数字是自陈**，两者证据等级不同

- **n=11 队、单场比赛、每队单次运行、无区间**

⟹ ⭐⭐⭐ **这与我那份「成本口径不一致」清单是同一类错误的营收版**（清单现有三项：自算硬件成本 vs 他人 API 报价 / 单价比值 vs 实测每任务花费 / 缓存命中 vs 未命中 = 50×）。**本条新增的是 gross vs net 收入确认口径。**⭐ 而**文章主动做了这个折价**，这在中文消费级科技报道里是个正面样本（我此前多次因单源未核实而给量子位打折）。

**② ⭐⭐ Anthropic 正商谈以约 60 亿美元收购芯片优化公司 Decart，以进一步控制推理成本、甚至补上部分芯片设计能力** ⟹ ⭐⭐⭐ **「成本战线上移到硅片」这条线的第三个数据点，且性质是新的**：前两个是 **AMD 收购 Taalas**（[[tech-blogs/2026-W32f]]）与 **4.8 亿美元砸向端侧 agent 芯片、首颗已量产**（[[tech-blogs/2026-W33h]]），都是芯片侧的动作；**本条是模型实验室自己去买推理成本能力。**

⭐⭐⭐ **而它与我上周记的「DeepSeek 涨价 50–1000%」在同一个读法下自洽：如果单位算力的采购价不再可靠下降，那么单位推理成本就从「可以租」变成「必须拥有」的战略资产。**⟹ 这直接加强我在 [[weekly/2026-W33]] §2 做的那处更正（「同等能力的单位成本」仍降 ≠「具体价格 / 单位算力采购价」必降）——**买芯片能力这个动作，只有在后者成立时才是必要的。**

⭐⭐ **另一条我认为原创的连接**：文章把 Anthropic 增长归因于**企业客户 + Claude Code**，并给了黏性论证「企业一旦把 Claude 接入代码开发、金融分析等核心流程，通常不会轻易更换模型」。⟹ ⭐⭐⭐ **而这恰好是 harness 主线的商业面：如果 harness / skill 是与模型配对的（SKILLER 测出为强模型写的技能会让小模型变差、Macaron-V1 的带版本 model-harness 配对），那么切换成本的一部分就是 harness 本身——换模型不只是换 API，是要重新推导那一百条技能。**⭐ **而今天 §1 里 Stanford 那个「100+ 条技能的 playbook」正好给这个切换成本一个具体的量。两篇今天同时到的文章，各给了这个论证的一半。**
