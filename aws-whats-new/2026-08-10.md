### 结论 2：更正 [08-09 日报](2026-08-09.md) 的「周五是发布高峰」——发布高峰其实是**周四**

08-09 那份表统计的是**日报文件的条目数**，而日报的 24h 窗口是「前一日 09:04 → 当日 09:04」，**主体落在前一天的下午（UTC）**。所以：

> **日报口径的「周五最密」（均值 11.8）⇔ 发布口径的「周四最密」（均值 13.2）** —— 两者不矛盾，是同一事实错位了一天。真正的发布高峰是**周四**，周五发布量反而低于周一/周二（8.2 vs 11.0/11.6）。

这一条对**抓取口径**有直接含义：日报标题里的日期从来不是「那天 AWS 发了什么」，而是「那天之前 24h 发了什么」，**跨了一次日界**。引用某天日报的条目数去讨论 AWS 的发布行为时必须先做这个平移。

## ⚠️ 更正：08-09 日报对「修复何时被真实 cron 检验」的判断是错的

[08-09 日报](2026-08-09.md) 末尾写：「⏳ 尚缺一环：真实 cron 触发下的验证。明天（周一）09:04 是下一次机会。」**这个判断不成立**，原因是它弄错了触发条件：

- cron 每天 09:04 跑一次，写的是**当天新文件**（今天写的是 `2026-08-10.md`）。**新文件里没有任何手写内容可保留 → 根本不会走到合并写分支。** 今天 09:03:42 那次 cron 的输出确实是 `0 items, 0 prose lines kept`，`0 prose lines` 恰恰说明它没被考到。
- 该 bug 的目标场景是**同一日期被跑第二次**。08-09 之所以触发，是因为那天 08:47 有一次手动补抓在前、09:04 的 cron 在后。
- ⭐ 所以结论要反过来写：**「每天一次的 cron」永远不会单独检验这个修复；它只在「手动补抓 ⊕ cron 落在同一天」时才被考到。** 而这正是补抓日的常态 —— 也就是说，这个修复**只在最容易出事的那些天生效**，平常一直空转。

**本次的真实检验（同日第二次运行）:** 本文的全部手写章节写入后再跑一次脚本 —— 见下节记录。

1. **22,465 条全量历史该不该用起来?** 目录 API 的 `totalHits` 是 22,465，理论上可以回溯到 What's New 开设以来。是否值得抽一次长周期（比如 12 个月）统计，看**周末硬零**是长期规律还是近期政策？以及 re:Invent 周（11–12 月）会把节律打成什么样？
2. **应不应该把日报的口径改成「按发布日」?** 现行 24h 滚动窗口导致每份日报都跨日界（见结论 2）。改成「昨日 00:00–23:59 UTC 发布的公告」会让日报与 AWS 的发布日一一对应、统计不再需要平移；代价是当日下午的公告要延后一天出现。**倾向：先在文件头把窗口区间写清楚，不动逻辑** —— 口径改动会让历史日报不可直接比较。
3. **合并写修复既然只在补抓日生效，要不要给它一个不依赖偶然的回归测试?** 今天是靠我手动制造「同日第二次运行」才考到它。一个 3 行的 pytest（写入含手写章节的文件 → 跑一次 → 断言章节仍在）比「等下一次补抓」可靠得多。
