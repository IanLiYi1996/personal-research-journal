### 1. ⭐⭐⭐ AgentCore Memory 加细粒度访问控制：权限正在被**往外推**，而这恰是一条可区分预测的正面数据点

两条 AgentCore Memory 公告 **pubDate 完全相同（08-28 20:00）＝同一批次**，而它们是设计上的一对，不是两个巧合的特性：

- **[flexible namespace variables](https://aws.amazon.com/about-aws/whats-new/2026/08/agentcorememory-flexible-namespaces)** 给出**划分轴**：在 memory resource 上定义键（**上限 5 个**）、在 strategy 的 namespace 模板里引用、运行时经 `CreateEvent` 传值，服务在长期记忆抽取时替换；目的是按 organization/tenant/team/environment 等维度切分而**不必复制 strategy 或滥用内置变量**；所有已 GA 区域可用、**不额外收费**。
- **[fine-grained access control (FGAC)](https://aws.amazon.com/about-aws/whats-new/2026/08/agentcorememory-fine-grained-access-control)** 在那个轴上**做强制**：用 AgentCore Gateway 前置 Memory、OAuth (JWT) 认证、挂 **Cedar 策略**；可以限定「每个用户只能访问自己 actor 的数据」、**把记忆记录限制在由用户 token claims 推导出的 namespace 上**、并按调用者允许/拒绝具体 Memory 操作。底层是 AgentCore Memory connector，**把 12 个 Memory 操作暴露成 Cedar action**，其请求属性可用作策略条件。
- ⭐⭐⭐ **最该引的一句是官方自己写的**：「This lets you move access control enforcement **from application code to the infrastructure layer** using **cryptographic proof of identity**.」
  - ⭐⭐⭐ **这直接落在 [[tech-blogs/2026-W35]] 深读的那条可区分预测上**：Latent Space 那篇论证 harness 的演化度量是「你能删掉多少」，并预测被吸收进权重之后**剩下的是 permissions / identity / trust / legibility**；⟹ **那四项应当表现出「继续被往外推」而不是「被训进权重」的模式**。本条是这条预测的**第四个数据点，且是最强的一种——一个已出货的托管服务，公告原文就把方向写成「从应用代码移到基础设施层」**（前三个：SemaPLC 的 verification-gated harness、Cloudflare 的按任务授权、Runtime Contract 的提交闸门；**仍然没有任何一篇在说把权限训进权重**）。
  - ⭐⭐ **也对上 StateM 给控制层设计空间提的那一轴**：「The distinction is not whether a system has state, but **who can inspect, modify, and operate the stateful control layer during execution**」—— Cedar 策略挂在 gateway 上、由人与基础设施操作，**被约束的 agent 自己动不了它**；这与 Runtime Contract 那面承重墙（验证器可访问外部参考状态、但没有 agent 内部状态的访问权）是同一取向。
- ⭐⭐⭐ **但必须把它放对位置：这是 Runtime Contract 二分法里的「预防面」，不是「证据面」。** FGAC 强制的是**能不能做**，它没有说会不会留下一份**可检验的「谁授权了这个动作」的记录**。
  - ⭐⭐⭐ **而昨天（08-27）深读的那篇 LessWrong 恰恰论证「缺的正是那个记录」**：它的缺陷定义是「Perform it both ways and receive the **exact same artifact**, such that downstream recipients have no means of telling apart what they got」，两个真实案例（retire.js 的 `--insecure`、Langfuse 的策略自动批准）**宽松度一点没改、只有「记录」变了**（approval source 三取值）。⟹ ⭐⭐ **对 FGAC 该问的因此不是「够不够严」而是「一次 Cedar allow/deny 是否落进一份可与『根本没评估策略』区分开的产物」** —— 公告没说，我也没读开发者指南，列为 Open Question。
  - ⭐ **同时它给昨天那个「四字段」补上了一格**：`prerequisite / authority / fallback / execution consequence` 里，**`authority` 正是权限性质的**，而 FGAC 用 JWT claims + Cedar 提供了它的**强制**版本；⚠️ 但那篇实测出的教训是「**闸门是围堵不是修复**」（固定 artifact 后下游验证消除了禁止动作，而 artifact 失活仍是 95.3%）⟹ **FGAC 挡住越权访问，挡不住一个已经在产物里被降级成 caveat 的约束继续传播。**
- ⭐⭐ **「12 个操作」这个数字本身有信息**：它是一个**静态可枚举**的动作面，而 Agentic Transaction 那篇点出的 Semantic Isolation 难点是「**conflicts often cannot be identified in advance because agents discover resources dynamically during execution**」⟹ **Cedar-on-12-actions 解决的是可枚举的那一半（操作），没有触及动态发现的那一半（资源）。**
- ⭐ **另与我追的「记忆不能只当检索」那条线（已 8 个位置）互补**：那条线批评的是**内容**面（记什么、该用时用不用），FGAC/namespace 是**治理与隔离**面 —— 与 Governed Persistent Memory 的 source-bound 状态语义 + fail-closed release 同层，⚠️ 但 FGAC 管的是「谁能读」，**不管「被取代/被撤回的记录还能不能支撑一条对外主张」**，那仍是空缺。

### 3. ⭐ CloudWatch agent 支持 journald：结构化日志替代「先落地成文本再解析」

- 机制与理由都写得很具体：**Amazon Linux 2023 等现代发行版已把 systemd journal 当主日志系统、默认不再写 `/var/log/messages` 这类文本文件**，此前用 CloudWatch agent 收这些日志需要额外配置把 journal 导出成文件；现在直接原生读 journald，**保留 journald 捕获的结构化元数据（systemd unit、priority、进程信息）**，并支持按 unit / priority / journal field 过滤与发布前的正则过滤以控量控成本。全商业区与 GovCloud(US) 可用。
- ⭐⭐ **接「过程可观测性」这条线，而且是它比较少见的「基础设施侧」一格**：r/programming 那条 flight recorder 帖的论点是「日志与 agent 自述的共同弱点是只包含作者当时想到要记的东西」；journald 原生读取是**从「解析别人格式化过的文本」移向「读结构化记录」**，⭐ 方向相同但幅度小得多（它不产生新信息，只是不再丢掉已有的元数据）。
- ⭐ 也对上 Runtime Contract 那份 12 系统 × 6 维度审计里的**结构化日志 7/12** —— 厂商在补「产出证据」的能力，⚠️ 而那份审计里真正的缺口是**提交闸门 2/12**，本条不动那一格。
