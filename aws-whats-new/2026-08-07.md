## 小结与趋势

**两条 High 都是 AgentCore,且合起来是同一件事:agent 从「函数」走向「有状态的长期进程」。**

1. **[Runtime instances GA](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-bedrock-agentcore-runtime-instances-generally-available/)** —— 在原有 **microVM** 之外新增「跑在你自己 EC2 实例上」的选项,由 AgentCore 代管 provisioning / 打补丁 / 扩缩 / 生命周期。要点:
   - 通过 **capacity provider** 指定实例族(**GPU 加速 / 内存优化 / 计算优化**),把 agent 挂上去
   - **单次 agent 会话最长 14 天**
   - 定位明确针对「**持续运行、资源密集、需要专用硬件**」的 agent
2. **[Temporal policies + rate limiting](https://aws.amazon.com/about-aws/whats-new/2026/08/temporal-policies-agentcore/)** —— 两个新控制面:
   - **Temporal policies(有状态授权)**:按 agent 在**同一 session 内的先前动作**来评估当前请求。官方给的理由很到位 ——「**单个 tool call 孤立看是安全的,但放在它之前发生过的事情的语境里可能是有害的**」。可强制工作流顺序、要求某个 tool 参数**必须精确等于前一次调用的输出**、特权动作前**要求人工批准**、以及强制数据新鲜度。
   - **Rate limiting**:按 OAuth / IAM 作用域,对 gateway 后面的 tools/models/agents 限流 —— 请求数、推理 target 的 **token 数**、并发连接数三个维度。

**我的读法:** 这两条呼应了本仓库最近几周反复出现的主线。14 天长会话 + 有状态授权,正是 [[2026-08-04-blog-openai-gpt-live]] 里「长会话暴露内存与持久化压力、容量不是 GPU 吞吐而是并发会话数」的同一问题在 AWS 侧的产品化答案。而 temporal policies 的立论(**单步安全 ≠ 序列安全**)与 [[weekly/2026-W32]] 记的「agent 破坏从厂商侧下沉到用户侧」(Fable 5 删 220 万文件)是同一枚硬币:**破坏往往不是某一步越权,而是一串各自合法的步骤**。把授权判断从「单请求」抬到「会话轨迹」,是目前少见的、真正对上这个失效模式的机制。

**其余 16 条无主线**,是常规增量:WorkSpaces 双发可观测性指标、ElastiCache 上 Graviton4、ECS 支持 G6f 的**分数 GPU 调度**、Lambda 控制台接 **Kiro / Cursor**、AWS Backup for S3 支持直接访问备份数据。
