## §1 Nemotron 3.5 Lightning：三条主线同时命中

规格（均出自公告原文）：**混合 MoE，30B 总参 / 每次前向仅 3B 激活**；从 **Nemotron 3 Ultra 蒸馏**；吞吐 **~410 tokens/sec，最高 4× / 任务完成快 30%**（对比「comparable models」）；**靠 DFlash 投机解码支撑至多 1M tokens 上下文**；完全用开放数据集训练，企业可自行后训练并在边缘/本地/云自主部署。定位词是 **"persistent agent workloads"**，举的场景是个人助理、金融文档处理、**网络安全 triage**、电信运维。

**(a) ⭐⭐ DFlash 第三次出现 —— 但它不能当作我昨天那个「up-to 阶梯」的第四级。**

昨天在 [[research-notes/2026-08-12-muse-glimmer-30b-deep-dive]] 里我把同一技术的加速倍数排成三层：**DFlash 论文自称 >6× 无损 → NVIDIA 宣传最高 15× → Meta 出货实测 3.1×**。今天很容易顺手把「4×」接成第四层，**但那是错的**：

| 数字 | 分母 / 口径 |
|---|---|
| 论文 >6× | DFlash **相对无投机解码基线**的无损加速 |
| NVIDIA 15× | Blackwell 数据中心卡上的 up-to |
| Meta 3.1× | RTX 5090 / batch=1 / greedy **实测** |
| **今天的 4×** | **整个模型 vs「comparable models」的吞吐** —— 不是 DFlash 的单独贡献 |

> ⭐ 所以正确记法是：**DFlash 已在三处独立出现（论文 / Meta 出货 / NVIDIA 自家模型），但这四个数字里只有前三个可比。** 这本身就是「口径不一致时不要把数字堆成阶梯」的一个现成例子，与昨天 BDH-CQ 那条（自算硬件成本 vs 他人 API 报价，论文披露但未量化）属同类。
> ⭐ **另有一个我此前没见过的用法值得单记：DFlash 在这里被说成是「支撑 1M 上下文」的手段，而不是提速手段。** ⚠️ 公告只有一句话、机制完全没说明，我不清楚投机解码如何支撑 1M 上下文（合理猜测是与块状草稿机制配合摊薄长序列解码成本，但**这是猜测，不要引用**）。

**(b) ⭐⭐ 「integrates directly with popular agent harnesses」—— 厂商把 harness 兼容性写进模型卖点，这是第二家。**

第一家是 Muse Glimmer 的 model card 把 scaffold 兼容性（OpenClaw / Hermes Agent）当作一项**模型能力**交付。⚠️ **而两家都没给跨 harness 分数。** 按 A²E 的结论（9 harness × 23 benchmark 共享同一骨干，**单轮问答九个 harness 分数完全相同、分化只出现在多轮任务**）与 SWE-Bench ProMax 的 scaffold 效应（GPT-5.2 从 mini-swe-agent 21.8% → OpenHands **41.2%**）：

> ⭐⭐ **「声称兼容多个 harness、却只报一组分数」等于没有回答「在哪个 harness 下」。** 这条现在可以当成一个稳定的验收问题去问任何模型厂商，而且 A²E 还顺带给了它的边界条件 —— 如果对方反驳「我们测了，换 harness 没区别」，要先确认那是不是**单轮评测集**（在单轮上九个 harness 分数全同，说明的是尺子没有分辨率，不是 harness 不重要）。

**(c) ⭐ 「persistent agents」作为模型定位词** —— 「agent 从一次调用变成长期进程」这条线的**第四种表达，且第一次来自模型/芯片厂商**而不是 harness 或云服务：Ouroboros 的 161 天常驻 → AgentCore 单会话 14 天 → Muse Glimmer 的 always-on 本地 agent → **今天 NVIDIA 拿它当模型的主定位**。

## §3 Bedrock 成本归因扩到 bedrock-mantle：兼容端点从「可观测」走到「可归因到身份」

⚠️ **先说清一件事实的来源。** `bedrock-mantle` 不是新名字，[W24 日报](2026-W24.md) 记过它（06-01 那条 CloudWatch 指标）。为了不靠 URL slug 猜，我**直接取了 06-01 那条公告的原文**确认它是什么：

> "The bedrock-mantle endpoint supports the **OpenAI Responses API, OpenAI Chat Completions API, and the Anthropic Messages API**, letting customers run existing OpenAI- or Anthropic-based applications on Amazon Bedrock with minimal code changes."

也就是**兼容端点** —— 让存量 OpenAI / Anthropic 应用几乎不改代码就跑在 Bedrock 上。于是这条公告落在一条清晰的两点轨迹上：

| 时间 | 给 bedrock-mantle 补的能力 | 粒度 |
|---|---|---|
| 06-01 | CloudWatch 指标（`AWS/BedrockMantle` namespace，推理次数 / 输入输出 token / 客户端错误） | account、project、model、project-and-model |
| **08-11** | **IAM principal 成本归因**（cost allocation tags + CUR 2.0 勾选 "Include caller identity (IAM principal) allocation data"） | **IAM 用户 / 角色 → 团队、项目、成本中心** |

**读法：兼容端点正在被补齐治理能力 —— 从「可观测」到「可归因到身份」。** 06-01 已能按项目/模型归因，今天加的是**身份轴**。AWS 在兼容端点（而非只在原生 `bedrock-runtime`）上补这些，说明他们预期那里跑的是真实生产流量，不只是迁移试验。

> ⭐⭐⭐ **对 agent 场景的具体含义，值得单独记：agent 是以 IAM role 的身份调用的，不是以人的身份。** 所以「这笔钱是谁花的」在 agent 工作负载里**只有到 principal 粒度才答得出来，而且答出来的是那个执行角色，不是发起任务的人**。要把成本真正落到人身上，得在 role 之外自己维护一条「任务发起者」的传递链。
> ⭐⭐ 这正好接上 [[reddit-digests/2026-W33b-reddit-hot]] 记的 r/devops 那条「内部平台 API 的 per-user token 怎么做」：**当调用方从人变成 agent，`per-user` 这个概念不只在授权维度要重新定义，在计费维度同样要。** 两个维度是同一个身份模型问题的两面。

这条整体落在 [[tech-blogs/2026-W32h]] 记的「成本议题从厂商定价转向企业内部管控」主线上，且属于**最底下那层基础设施**：要管控，先得能归因。

## §4 Secrets Manager 托管轮换：一个「切换前先验证」的干净实例

新增 **Jenkins API Token** 与 **SonarQube Token**（后者细分 User / Global Analysis / Project Analysis 三类）的托管轮换，无需自写轮换代码。两处机制细节值得记：

1. ⭐⭐ **"mints a new token and revokes the old one only after the replacement is verified active"** —— **先确认新凭据确实可用，再吊销旧的**，好让 CI/CD 作业不中断。这是「写入/切换前先验证」这个模式在凭据轮换上的实例，与本仓库反复出现的准入闸门同构（LongHorizon-Harness 的 executor 声明不能直接改状态 / SkillJack 那条的 pre-commit gating / [[tech-blogs/2026-W32b]] 记的「写入前设准入闸门」）。
2. ⭐ **self-rotation（被轮换的 token 自己认证其替代品）vs admin-assisted rotation（另有一个 admin token 执行 generate + revoke）** —— 这个区分对 agent 很实际：**要让 agent 持有的凭据自轮换，就必须允许它用旧凭据换新凭据**，这是一项真实的权限扩张；用 admin-assisted 则把这项权力挪出 agent 之外。选哪个是安全边界决策，不是实现细节。

托管名单现扩到 11 家（BigID、Confluent Cloud、Datadog、GitLab、MongoDB Atlas、Okta、Paddle、Salesforce、Snowflake + Jenkins、SonarQube）。⭐ AWS 在做的是**第三方凭据轮换的托管层**，对 agent 安全的含义是减少长期静态凭据 —— 而长期静态凭据恰恰是这两周记录的那一串 agent 越权事故里最常被拿走的东西。

## ⭐⭐⭐ 10:57 二次运行：把「AWS 同日二次抓取值不值得」这个未测项测掉了

**本次（10:57 UTC）是今天的第二次运行**（首次 09:11 由 cron 触发）。⭐ **产出为零条新增，但这次「零」本身是我要的那个数据点。**

**CLAUDE.md 里这条一直是个推测:**
> ⭐⭐ 同日二次抓取只有 HF 值得（2026-08-11 三个数据源实测）……**AWS 未测，但同属「按发布时间的流」，推测同样不值得。**

**现在测了。四个数据源的表可以补全:**

| 数据源 | 同日二次抓取的收益 | 依据 | 根因 |
|---|---|---|---|
| ⭐ **HF Daily Papers** | ⭐ **有价值** | 当日桶 **0 → 20 篇**（今天 05:xx → 17:4x） | **当日桶持续回填**当天投稿 |
| **Reddit** | ⚠️ 无 | 4 小时内真新增 **1 帖**（按发布时间戳） | top-of-week 是**周聚合排名** |
| **tech-blogs** | ⚠️ 无 | 3 小时内新增 **1 篇** | RSS 是按发布时间的流、博客发布本身低频 |
| ⭐ **AWS**（本次） | ⚠️ **无（已实测）** | ⭐ **1.77 小时内新增 0 条**；`diff` 只有抓取时间戳一行变化 | ⭐ **纯时间序、不回填，且窗口是固定 24h 回看** |

> ⭐⭐⭐ **而 AWS 这条的根因比其余三个更硬，值得单独说清:HF 值得二次抓取是因为「同一个日期桶的内容会变」；而 AWS 的 RSS 是纯时间序、从不回填，所以同日第二次运行看到的必然是同一批条目——除非在两次之间真的有新公告发布。**
> ⭐ **也就是说 AWS 的二次抓取不是「收益低」，而是「收益完全取决于这段时间窗里有没有新发布」。** 今天 09:11 → 10:57 这 1.77 小时里没有，所以是零。**这不是概率问题，是机制问题。**
> ⭐⭐ **可操作结论:AWS 日报每天一次即可；若真想抓当天产出，正确做法不是「同日多跑」而是「把抓取时刻推后」** —— 而按今早那节的统计（27 天里 67% 的日子首条早于 09:04），09:04 这个时刻本身已经够用，多数日子能吃到部分当天产出。
