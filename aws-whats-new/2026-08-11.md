## ⭐ 本日最值得记的一条：EC2 application status checks

[Amazon EC2 introduces application status checks](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-ec2-application-status-checks)（08-10 17:47，脚本判 Medium）

**AWS 自己把缺口说得很清楚（引原文要点）:** 客户此前依赖 EC2 status checks 得到的是「**实例或底层系统不可达**」的告警；而要监控**应用层**问题（web server 停止接受请求、Docker daemon 没在跑、网络配置错误、网卡不再过流量），**客户必须自建并维护监控方案**。现在可以指定协议与端口，让应用层检查与既有的 instance / system status checks 并列。

> ⭐⭐ **为什么我认为这条比 9 个新模型更值得记 —— 它是一个我一直在追的错误类型的平台侧修补:**
>
> **「实例可达」≠「应用可用」。** 被测的信号比你真正关心的东西低了一层,而低那一层的信号看起来一切正常。
>
> **这与我这周在 [[topics/agent/2026-08-07-agent-eval-briefing-for-sharing]] 里反复写的是同一个错误类型:**
> - **agent 评估:** 「agent 自报完成」≠「任务实际完成」→ 对策是核对环境的客观终态，而不是读它的过程描述（[[tech-blogs/2026-W32h]] 记的 OSReward 实测:裁判主要在读 agent 自述,困难集上最好的裁判只有 69.7%）
> - **EC2:** 「进程/实例活着」≠「应用在服务」→ 对策是在应用层加一个独立检查
>
> **两边的结构完全一样:低一层的健康信号会稳定地给出假阳性,而修法都是「在你真正关心的层次上加检查」,不是把低层信号做得更精细。**
>
> ⚠️ **一个我要克制的地方:** 这是类比,不是同一个技术问题。EC2 这条是运维监控,不涉及"被测对象有动机误报"这一层 —— **agent 场景多了一个"自报者可能在优化分数"的对抗性,比单纯的层次错配更难。** 类比到此为止。

## 关于零条分支修复的验证状态（更正我此前的说法）

[[aws-whats-new/2026-08-09]] 里我写「下一次真实检验是周一 09:04」。**现在可以把这句说清楚:**

- 08-10（周一）09:03:42 的 cron 确实跑出了 `0 items` —— 但那次是**新建文件**（当时文件里还没有手写内容），**并不触发那个 bug**。bug 只在「文件里已有手写内容 + 该日 0 条 + 脚本再跑一次」时触发。
- ⭐ **所以「等真实 cron」这个说法本身是我设错了验证目标。** cron 执行的就是同一条命令（`uv run python3 scripts/aws_whats_new.py`），**cron 与手动运行走的是完全相同的代码路径** —— 我此前把它当成一个独立的验证维度，是多余的。**真正该验证的是那个代码分支，而它已经验证过了**（0 条 + 已有 prose → `0 items, N prose lines kept`，且连跑幂等）。
- **本日 8 条，走的是非零分支**，今天 09:04 的 cron 会顺带再测一次 prose 保留（非零路径此前一直是好的）。
