## 小结与趋势

### 1. ⭐⭐⭐ 「skills」成为 AWS 官方产品交付物，而它落在我 08-20 深读那篇的两个负面结果上

[Amazon Redshift integrates with Agent Toolkit for AWS](https://aws.amazon.com/about-aws/whats-new/2026/08/redshift-agenttoolkit-for-ai-assisted-datawarehouse-mgmt) 是本份对我主线最有实质的一条。它把两个部件配成一套：**AWS MCP server**（代你执行经认证的 AWS API）＋ **Redshift skills**，后者被定义为「curated packages of **tested procedures and reference material** that help AI agents complete Redshift tasks more effectively」。

⭐⭐ **内容构成与 [[2026-08-20-hf-daily-papers-aug18-20]] 深读的 Demystifying Agent Skills 测出的机制一致，而不是与直觉一致**：那篇的结论是技能靠「流程锚定」起作用（65.7%）而非「注入知识」（4.5%），原话 "skills usually do not work by supplying missing facts. They work by **stabilizing action**"。AWS 列出的 skill 内容正是流程性的 —— SQL 语法参考以**减少查询生成错误**、元数据发现、数据加载模式、物化视图最佳实践、以及端到端迁移的分步（discovery → schema/SQL conversion → data movement → validation → performance comparison）。⟹ 厂商侧独立地把 skill 做成了流程锚定物。

⚠️⚠️ **但那篇的两个负面结果直接适用，而公告的措辞恰好朝它们走**：

- 公告写「We will continue to expand these skills with additional capabilities over time」。而 Demystifying Agent Skills 测出**技能池从 5 涨到 100 时，执行期实际使用精度从 29.6% 崩到 3.3%（Gemini 16.9→0.7 / Codex 42.3→5.9），而下游成功率 36.4%→39.3% 几乎不变甚至微升** ⟹ 「扩充覆盖面」与「该用哪条选得准」是两个量，而只有后者会崩。⭐ 与 StateM §4.7「experience must be filtered before it becomes memory……The objective is to remember the consequential boundary, not every failure trace」是同一警告。
- 更该记的是那篇被摘要忽略的发现：**技能是用一类失效换另一类** —— SC2（执行/验证失效）197→124，而 **SC3（调用/适用性/边界失效）19→78 ≈4 倍，且这一类在没有技能时几乎不存在**。⟹ 装上 Redshift skills 之后要盯的新失效不是「SQL 写错了」而是「在不该用这条技能的场合用了它」。

⭐⭐⭐ **而公告同时点名三个 harness（Claude Code / Kiro / Cursor）共用同一套 skills，这与 [[2026-08-14-hf-daily-papers-aug14d]] 的 SKILLER 直接冲突**：那篇测出为强前沿模型写的技能注入紧凑模型后「frequently yield suboptimal gains or **even degrade performance**」，并由此得出「skill 是 model–harness 配对的一半、报 skill 效果不写执行者等于没报」。⟹ **一套 curated skills 供三个 harness、任意底层模型使用，正是那篇说不成立的那个假设**。⚠️ 我不据此断言 AWS 这套会失效（Redshift 任务的技能可能比 SKILLER 测的 agent 任务更接近「参考手册」而非「行为约束」，而参考型内容的迁移性应该更好），但这是一个**可检验**的缺口：同一套 skills 在 Claude Code 与更弱执行者下的分数差就是它的估计值。

### 2. ⭐⭐ 我自己的 Muse Glimmer 深度调研被 AWS 的公告独立逐项对上，而顺带暴露一个定位张力

[Muse-Glimmer-30B and Qwen 3.8-27B on SageMaker JumpStart](https://aws.amazon.com/about-aws/whats-new/2026/01/muse-glimmer-30b-qwen-3.8-27b-on-sagemaker-jumpstart/) 的描述给出：**30B dense / ~1.8B ViT-G/14 感知编码器 / 131K+ 上下文 / 可选推理强度（low 到 extra-high）/ Apache 2.0**。⭐ 这四项我在 [[2026-08-12-muse-glimmer-30b-deep-dive]] 里全部是从 `config.json` 与 GGUF 实际文件大小复算出来的 —— **一个独立来源逐项对上，是对那份笔记事实层的检验通过**（⚠️ 但它对不上的是那份笔记的原创部分：KV 预算复算与基准分裂的读法，公告不涉及）。

⭐⭐ **张力值得记：公告用「operates entirely without cloud infrastructure which is ideal for always-on enterprise agents」当卖点，而它出现在一条「上 SageMaker JumpStart」的云服务公告里。** 不是矛盾（企业要的是托管部署而不是「必须联网」），但它说明那句「无需云基础设施」在厂商叙事里是**能力描述**而非部署建议。⭐ 而「always-on enterprise agents」这个用词正接上我追的「agent 从一次调用变成长期进程」那条线（Ouroboros 161 天 / AgentCore 单会话 14 天 / Muse Glimmer always-on），这是第一次由**云厂商**用这个词描述一个模型的定位。

⚠️⚠️ **一个我提不出答案但该问的：公告把「selectable reasoning strength（low through extra-high）」列为特性，却没说 JumpStart 上的默认值是哪一档。** 而 [[tech-blogs/2026-W34]] 记的 Simon Willison 实测正是 **Qwen3.8-27B 默认 `xhigh`，在消费级硬件上「画一个圆」也进 22K token 推理、pelican SVG 花 21 分钟**。⟹ 这两个模型现在装在同一条按 token 计费的托管服务上，**默认档位直接决定账单**，而这恰是我归纳的「算力分配四个层面」里最容易修的那个（单题·配置侧）。

### 3. ⭐⭐ 「知道转移的控制面」在运维领域是成熟工程，而 agent 侧还在论文里 —— DRS Recovery Plans 是干净的对照

[AWS Elastic Disaster Recovery introduces Recovery Plans](https://aws.amazon.com/about-aws/whats-new/2026/08/elastic-disaster-recovery-plans/) 三个要素同时具备：**顺序状态（group servers into sequential steps）＋ 显式等待/退出条件（configurable wait times between them）＋ 人工批准闸门（add approval steps where you want a person in the loop）**，另有非破坏性 drill mode 用来验证流程本身。

⭐⭐⭐ 这几乎逐项对上 [[2026-08-20-hf-daily-papers-aug18-20]] 深读的 StateM（状态即「上下文与契约的边界」，进入刷新指令、离开须满足显式退出条件）与 Runtime Contract 的「非幂等动作导向人工批准」。⚠️ **但要点在于它不是 agent 产品** —— 它是传统编排，而这恰好是 StateM 那句批评的反面例证：StateM 说通用 CLI agent 的「plans, instruction files, memories, and hooks **do not by themselves form a unified, transition-aware control surface**」。⟹ **同一个东西在灾备编排里是有产品有 drill mode 有批准步骤的成熟品类，在 agent 侧还是一篇没做消融的论文。** ⭐ 沟通上这比任何论证省力：给运维团队讲 agent 控制面时，指着他们已经在用的 Recovery Plans 说「agent 缺的就是这个」。

### 4. ⭐⭐ Aurora DSQL 外键约束：把约束放在数据层，就绕开了 08-27 那条「约束降级」通道

补录那条 [Aurora DSQL now supports foreign key constraints](https://aws.amazon.com/about-aws/whats-new/2026/08/aurora-dsql-foreign-key-constraints/) 的机制是 fail-closed：「Aurora DSQL then **refuses any write** that would leave that customer pointing at an address that no longer exists」，并把删除/更新行为做成 NO ACTION / RESTRICT / CASCADE / SET NULL / SET DEFAULT 五个显式选项。

⭐⭐⭐ 与我昨天（[[2026-08-27-hf-daily-papers-aug26-27]]）深读的 *When "Must" Becomes "Maybe"* 形成一个有用的对照。那篇的机制是：约束通过**中间语言产物**（summaries/plans/tickets/handoff notes）传递时，会从「必须在执行前解决」降级为「可以参考但不再决定下一步」，而内容仍在（`semantic availability ⇏ operational preservation`），正常的 handoff 压缩产生 **100% 失活**。⟹ **外键约束不经过语言产物，所以那条降级通道对它不存在。** ⭐⭐ 由此得到一条可操作判断：**能放进数据层的约束就不要只放进传给下游 agent 的产物里** —— 前者的执行不依赖任何一环把「必须」这个模态保住。⚠️ 代价当然是表达力（`prerequisite`/`authority` 这类授权状态没法写成外键），所以这不是替代而是分层。
