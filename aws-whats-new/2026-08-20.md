## 小结与趋势

16 条（14 在窗口 + 2 补录），量与结构都平淡，**没有一条是新服务或 GA 级发布**。但有两条组合起来构成今天唯一真正值得记的内容观察，另有一条运维/口径发现比任何公告都重要（见下一节）。

### ⚠️⚠️ 今天最该记的一条：同一天、同一厂商，两个产品在「默认是否安全」上走了相反方向

- **[Amazon Quick 的 deny by default](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-quick-deny-by-default/)**：原文把旧行为写得很清楚——「Previously, new AI capabilities were available to all users on release, **requiring administrators to react after the fact**」，新行为是「Quick then **denies any new AI capability at launch**」，且「Restricting a category also restricts existing capabilities in it」，管理员逐个显式放行。
- **[Bedrock Web Search 的 External Web Access](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-bedrock-web-access-web-search/)**：Web Search 本月刚发布时的卖点是「maintaining data within your secured AWS environment with **zero data egress**」，今天这条**把这个属性放开**——`external_web_access` 让它直接从公网取内容。⭐⭐⭐ **而原文那句配置说明值得逐字读：「grant the `bedrock-websearch:ExternalWebAccess` IAM permission to the request identity and **leave the `external_web_access` parameter at its default of `true`**」。**

⟹ ⭐⭐⭐ **两者合读得到一个我此前没有的区分：「默认安全」这个说法在多层架构里没有单一答案，要问「哪一层的默认」。** Web Search 这条的**有效默认是拒绝**（没有那条 IAM 权限就取不到公网），但**参数默认是 `true`**——即一旦权限被授予，egress 就是发生的，除非显式把参数设成 false。**闸门在 IAM 层，而不在参数层。** 这与 Quick 那条（闸门在能力层、默认拒绝、逐个放行）恰好是两种不同的安全默认设计。

- ⭐⭐ 对我一直在追的「权限边界必须在执行层而非模型层」有直接含义：**Quick 那条是我见过厂商侧最干净的 fail-closed 准入闸门实例**——它不是「检测滥用」而是「新能力出生即被拒绝」，与 [[tech-blogs/2026-W33h]] 记的 Governed Persistent Memory 的 fail-closed release、以及 W32f 记的 pre-commit gating 是同一模式。
- ⚠️ 而 Web Search 这条提醒我：**厂商在同一周里既会交付闸门、也会交付绕过容器的能力，两者不矛盾但必须一起读**——「zero data egress」这个曾被用作卖点的属性，现在是一个可以被一条 IAM 权限打开的开关。
- ⚠️ 我对 Quick 这条的分级与脚本不一致，且这是**第二次**：08-13 我就写过它「不是增量功能，是治理模型的变更」并判 High，脚本判 Medium。我仍判 **High**。

### ⭐⭐ 第二条：给 agent 检索加「时间窗口」成了运行时一等参数

**[Web Search in AgentCore 加 domain 与 published-date filtering](https://aws.amazon.com/about-aws/whats-new/2026/08/web-search-amazon-bedrock/)** —— 原文：「giving agents **per-request control** over which web sources and time windows they search」，published-date filtering 用「inclusive from and to date bounds」。

- ⭐⭐⭐ **这直接对上我追了很久的那条线：「答案在权重里 / 前视偏差」的干净解法都是「只用某个日期之后（或之前）的数据」**（SWE-Bench ProMax 只挖 2025-01 之后的 commit、Gaming Without an Attacker 与 Metal 套件选「预训练语料里基本不存在」的领域、金融侧的前视偏差）。**今天它第一次以「检索时的日期上下界」形式出现在厂商产品里**——对做回测类 agent 的人这是可直接用的原语（把检索窗口钉在决策时点之前）。
- ⚠️⚠️ **但有一个我认为论文侧的教训能立刻提醒的隐患：这个过滤是 per-call、由 agent 自己控制、且原文明说「without requiring admin reconfiguration」。** ⟹ ⭐⭐⭐ **一个由被评估方自己设定的时间边界，就落在优化压力之内**，而我这两周反复记的那一类解法恰恰要求「参照留在优化压力之外」（Gaming 的未披露轴 / PRISM 的冻结文本原型 / CW-BASS v2 的既存操作阈值）。**要用它防前视偏差，边界必须由 harness 在 agent 之外钉死，而不是交给 agent 每次调用自己填。** （我的推断——公告只讲能力不讲这个取舍。）

## 🚨⭐⭐⭐ 本次口径发现：feed 用两种 URL 形式发同一条公告，而我所有链接比较都是原始字符串匹配

**根因**：同一条公告会以 `https://aws.amazon.com/whats-new/...` 与 `https://aws.amazon.com/about-aws/whats-new/...` 两种形式出现（**slug 完全相同，只差 `/about-aws/` 前缀**）。而 `_already_covered()` 按原始字符串比对 ⟹ **同一条公告被当成两条。**

**代价（两处，都已实测确认）：**

1. **重复上报**：三条 Amazon Quick 公告在 08-13/08-14 与 08-18 **各报了一次**（approval-policies-sharing / dlp-purview / per-user-resource-limits）。
2. 🚨⭐⭐⭐ **污染了延迟数据，而且方向恰好让我做出错误结论**：因为第二次出现看起来像「迟到条目」，它们被判为补录，并按 08-14 的旧 pubDate 算出 **60–82h 的假延迟**，写进了 `backfill-delays.tsv`。⟹ **而这批点正是我 08-18 用来写下「延迟 60–88 小时、`BACKFILL_HOURS = 96` 只剩 8–36 小时边际、要考虑是否该升」的依据。**
   - ⭐⭐ **复核后的真实图景：那批四条里只有一条是真的**（`custom-no-data-message`，66.2–88.3h，只出现过一次、单一 URL，已逐条核实），另三条是假点。有效点从 9 个降到 **6 个**，**观测到的最大上界仍是 88.3h**，故 **96 既不该降、也不必急着升**——但「该不该升」现在只压在**一个**点上，不是四个。
   - ⭐⭐⭐ **一个值得单独记的自我审查结果：我的汇总数字侥幸对了，但理由是错的。** 我 08-18 写过「那批四条同属 Amazon Quick、其中三条在连续三分钟内发出＝**按事件聚合约 1 个事件**」——我当时把它降权到 1，理由是「同一次 feed 故障造成的相关点」；**实际是 1 个真点 + 3 个非点。** 结论（≈1 个事件）活下来了，机制解释是错的。⟹ **这类「答案对、机制错」的情形只能靠回到原始数据逐条核实才发现，靠检查结论的自洽性发现不了。**
   - ⚠️ 另外注意：我此前立过一条判据「任何用于检验某个安全边际是否够的测量，都要先确认它的偏差方向不是『让边际看起来更安全』」。**这次的偏差方向是反的（让边际看起来更危险），所以那条判据抓不到它。** ⟹ 判据应扩成「**先确认偏差方向**」，而不是只防一个方向。

**修法与影响面（按既有纪律，改之前先量）：**

- ✅ 加 `_canon_link()`，在**全部**链接比较点归一化（`_already_covered` / 窗口内去重 / merge-write 的 `fresh_links` / 延迟日志的 `already_reported`）。
- ⭐⭐⭐ **刻意用窄写法，且宽写法是被数据否掉的**：只剥 `/about-aws/` 前缀与尾斜杠，**保留 `whats-new/YYYY/MM/slug`**。在全部 digest 上实测两种写法——**只留 slug：7 处合并里 3 处是把不同公告误合并**（AWS 也会用裸服务名 URL 发不同公告：`.../2026/08/amazon-quick/`、`.../amazon-connect/`、`.../amazon-gamelift-streams/`，⭐ **而今天的 SageMaker 那条恰好就是这个形状 `.../2026/08/amazon-sagemaker/`**）；**只剥前缀：3 处正确合并、0 处误合并** → 采用窄写法。
