## 🚨 头条不是公告，是我昨天那个预测被证伪了

昨天那份 digest 里我写下**第一个可 falsify 的 AWS 节律预测**（[[2026-08-12]] 最后一节）：基于「首条时刻大量落在整点（07:00 出现 6 次，00:00/12:00/15:00 各 2 次）⟹ pubDate 有相当部分是排定的发布档位」这个观察，我预测 **08-12 的首条公告最可能落在 12:00 或 15:00 UTC**。

| | 内容 |
|---|---|
| 预测 | 08-12 首条落在 **12:00 或 15:00 UTC** |
| 实际 | ⭐ **17:09 UTC** |
| 判定 | ❌ **两个候选档位都没命中，且实际值比两者都晚** |

⭐⭐ **而且失败得比「猜错了一个档位」更彻底：17:09 是我这 400 条记录里 37 个有公告的日子中唯一一个 ≥17:00 的首条时刻**——其余 36 天全部在 16:00 之前开始。所以实际值不只是落在两个候选之外，它落在**整个已观测范围之外**。

> ⭐⭐⭐ **教训（比预测本身有价值）：那个「整点档位」观察其实是对的，但我把它用在了错的量上。**
> 看 08-12 这天的全部六条时刻：**17:09** / 17:15 / 17:15 / 18:00 / 18:00 / 22:00 —— **后五条全是整点或整刻，唯独首条不是。** 也就是说「多数 pubDate 落在整点档位」这个**描述性**规律在同一天内依然成立，失败的是把它当成**首条时刻的预测器**。
> ⭐ **为什么这个区分重要：档位现象说明的是「AWS 有排定发布窗口」，而首条时刻取决于「当天最早那个窗口有没有东西要发」——后者由内容供给决定，不由档位表决定。我把一个关于「时刻取值集合」的规律，错用成了关于「哪个时刻会被占用」的预测。**
> ⚠️ 这与我 08-11 自我更正过的错误**不是同一个**（那次是从单日观测概括出「必然」，样本量问题）；**这次样本量够（27 天），错在把规律套用到它约束不到的量上。** 记为第二类错误，两条都值得留着。

## ⭐⭐⭐ 内容主线：同一天同一家，两个默认值往相反方向动

六条里有两条都在改「默认给什么权限」，而**方向正好相反**——这是本份唯一值得展开的内容观察。

| | [Amazon Quick **deny by default**](https://aws.amazon.com/whats-new/2026/08/amazon-quick-deny-by-default-permissions/) | [IAM **role manager**](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-iam-role-manager)（GA） |
|---|---|---|
| 原状态 | ⭐ **「新 AI 能力发布即对所有用户可用，管理员只能事后补救」** | 开发者自己建角色，容易卡住或图省事给过宽权限 |
| 改成 | 管理员把整个 AI 能力**类别**设为受限 → **新能力上线即被拒**，需逐项显式放行 | ⭐ **控制台里配服务时自动按 AWS 托管模板建默认角色**（或复用已匹配的现有角色），首发支持 6 个控制台含 Lambda / EventBridge |
| 方向 | 宽松 → **收紧**（治理优先） | 手工 → **自动放宽起点**（便利优先，最小权限延后） |
| 收紧的路径 | 默认就是收紧的 | ⭐ 公告自己写明：**「ready to tighten 时请关掉 role manager 并用 IAM Access Analyzer 逐个精化」** |

⭐⭐ **一个能同时解释两者的读法：这条轴不是「宽松 vs 严格」，而是「设置成本落在谁头上」。** Quick 把成本推给**想要控制的管理员**（每个新能力都得显式放行）；role manager 把成本从**开发者**身上挪走，代价是初始权限按模板取并集而非按任务取交集。两条都是 defaults engineering，只是各自选了不同的人来承担摩擦。

> ⭐⭐⭐ **对我 agent 评估那条线的直接含义（本份最该记的一条）：**
> 我这两周从三条互不相关的证据独立得到同一个架构判断——**agent 安全必须在权限层与执行层约束，不能靠模型层拒答**（[[research-notes/2026-08-12-muse-glimmer-30b-deep-dive]] 的 AgentDojo ASR 28.4%、[[reddit-digests/2026-W33-reddit-hot]] 的健身课事故、[[tech-blogs/2026-W33d]] 记的 AWS-OpenAI「靠上下文而非靠拒答」）。**而 role manager 正好动的是这个判断所依赖的那一层：它让起始权限集变得更宽、且由模板而非由任务决定。**
> ⭐ **当「配 Lambda」这个动作的执行者从点控制台的人变成 agent 时，自动建出来的那个角色就成了 agent 的 blast radius，而它的边界是由 workflow 模板的权限并集划的，不是由这次任务实际需要什么划的。** 模板化 ≠ 任务化——模板按构造必须覆盖该 workflow 可能需要的一切。
> ⚠️ **但要说公道：这不是无界授权。** 公告明确说是 **AWS 托管模板、可检视、建出来的角色在 IAM 控制台里是标准角色且可识别哪些是 role manager 建的、随时可开关**。所以准确的批评只有一句：**模板作用域不等于任务作用域**，而非「它给了过大权限」。
> ⭐⭐ **更值得记的是收紧路径的形状：「关掉 role manager + 用 Access Analyzer 精化」是一个 opt-in 的第二步。** 这与 [[research-notes/2026-08-13-hf-daily-papers-aug12-13]] 里 Runtime Contract 那篇审计出的形状完全一样——**12 个公开 agent 系统里文件 diff 有 9/12、工具输出 11/12，而「提交闸门」只有 2/12；材料都在，闸门没接上。** 这里也是：精化工具（Access Analyzer）现成、模板可检视，但**默认路径不经过它**。⭐ 所以这条可以作为一个非 agent 领域的干净旁证进客户材料：**「闸门存在但默认不启用」不是 agent 圈的特有毛病，是 defaults engineering 的通病。**

### ⭐⭐ 第二条：AI 治理正在接进企业已有的合规工具，而不是另建一套

[Amazon Quick × Microsoft Purview DLP](https://aws.amazon.com/whats-new/2026/08/amazon-quick-dlp-purview/) 的做法是：**直接用客户已有的 Purview 敏感度标签**去驱动 Quick 里 chat / spaces / knowledge base 的文件处置，每个标签可配 **block / warn / allow**；公告举的例子是金融业把 "Highly Confidential" 标签的文件禁止上传到共享空间、"Internal" 放行但告警。原话是**「无需额外工具即可把已有的 Purview 治理策略延伸进 Quick」**。

> ⭐⭐⭐ **这与我昨天在 [[reddit-digests/2026-W33d-reddit-hot]] 记的那条最有用的长尾（r/aws 把 agent 评估放进 **MRM／模型风险管理** 话语而不是「基准分数」话语）是同一个结构性动作的两个实例：**
> **AI 治理不是长出一套 AI 专属控制项，而是被接到既有的企业合规工具上**——模型侧接 MRM，数据侧接 Purview 标签。
> ⭐⭐ **对客户材料的直接用处（这是昨天那条推论的加强版）：论证结构应该是「你们现有的 X 已经要求这些，agent 相比传统模型多出以下新维度」，而不是「agent 评估很重要，这是原因」。** 昨天我从 MRM 一个例子得到这条，今天有了第二个独立领域的例子 → **从「一个观察」升级为「一种可预期的落地模式」**，写方案时可以直接按这个模式找客户手里已有的那个 X。
> ⚠️ 保留：这两条我都只读到公告/标题层，Purview 集成的实际粒度（标签如何跟随文件进入 knowledge base 后的检索结果）公告未答。

## 小结与趋势

1. ⭐⭐⭐ **本份最有价值的产出是一个失败的预测，以及对失败原因的定位**：「多数 pubDate 落在整点档位」这个描述性规律为真，但**不能用来预测首条时刻**，因为首条由内容供给决定而非由档位表决定。这是与 08-11 那次（样本量不足）**不同类型**的第二种推理错误。

2b. ⭐⭐⭐ **而在做这份 digest 的过程中我又制造并当场推翻了一个准发现**：「低量日启动更晚」的 Spearman −0.477 / p=0.0039 **完全落在次序统计量零假设的模拟区间内**（模拟均值 −0.405，31% 的模拟比观测更负）⟹ 无剩余信号，我原来的置换检验**拒绝的不是我想拒绝的那个零假设**。⭐ 但同一个模拟证明 **08-12 本身扣掉低量效应后仍异常（给定 n=6，首条 ≥17:09 的概率 0.008）**。→ ⭐⭐ **可复用判据：相关性的一端是「某集合的极值」时，先算次序统计量零假设再谈显著性。**
3. ⭐⭐⭐ **同一天同一家把两个默认值往相反方向推**（Quick 收紧 / IAM 自动放宽起点），可用「设置成本落在谁头上」统一解释；⭐ 而 **role manager 的「模板作用域 ≠ 任务作用域」直接触到我 agent 权限边界那条主线**，且它的收紧路径是 opt-in 第二步——**与 Runtime Contract 审计出的「材料都在、闸门没接上」（submit gate 2/12）同形，可作非 agent 领域的旁证**。

## ⭐⭐⭐ 追加：我把上面那个 Open Question 当场测了，结果推翻了自己一半的说法

上面我本来把「08-12 的低量 + 极晚启动是同一原因吗」列为待查项，理由是「可 falsify 且我已有全部数据」。**既然如此就没有理由留到明天**——直接用那 400 条算了。

### 第一步：相关性确实很强

用 36 天（丢掉最旧那天，它被 400 条窗口截断故计数不完整）：

| 检验 | 结果 |
|---|---|
| Spearman(当日公告数, 首条时刻) | **−0.477** |
| 置换检验 p（双侧，20,000 次） | **0.0039** |
| 首条 <08:00 的日子 (n=21) 中位公告数 | **12** |
| 首条 ≥08:00 的日子 (n=15) 中位公告数 | **10** |
| ⭐ 最晚启动的 5 天里，有几天同时在最低量 5 天内 | **4/5** |

看到这里我几乎就要写下「低量与晚启动同源」了。

### ⭐⭐⭐ 第二步：但这个相关性有一个纯机械的解释，而它足以解释掉全部

> **如果一天只发 6 条，那么「这 6 条里最早的那条」平均就会晚于「另一天 20 条里最早的那条」——即使每条公告的时刻都来自完全相同的分布、量与时刻之间毫无因果关系。** 这是次序统计量（最小值随样本量增大而变小），不是发现。

于是我做了对应的零假设模拟：**保持每天的真实条数 n 不变，把时刻从全部 400 条的合并分布里 iid 重抽**，再算相关系数。

| | 值 |
|---|---|
| 观测 Spearman | **−0.477** |
| ⭐ 纯次序统计量零假设下的模拟均值 | **−0.405** |
| 模拟 95% 区间 | **[−0.652, −0.114]** |
| 观测值是否落在区间内 | ⭐⭐⭐ **落在内部（模拟中有 31% 比它更负）** |

> ⭐⭐⭐ **结论：那个 p=0.0039 的「显著」相关性完全能被样本量效应解释掉，没有任何剩余信号。** 置换检验测的是「量与时刻是否独立」，而它们在**机械上**就不独立——所以我一开始那个检验问错了问题：**它拒绝的零假设不是我想拒绝的那个。**
> ⚠️ 严格表述是**「无法排除纯机械解释」而非「已证明是假象」**：我的零假设假定日内各条时刻 iid，而实际时刻明显有聚簇（整点档位）与星期结构，真实零分布的方差会与模拟不同。

### ⭐⭐ 第三步：但 08-12 那天本身仍然是真异常

同一个模拟可以顺手回答一个更该问的问题——**给定那天只有 6 条，17:09 这个首条时刻算不算异常？**

| | 值 |
|---|---|
| n=6 时模拟首条时刻的中位 | **7.75h** |
| 实际 08-12 首条 | **17.15h** |
| ⭐ 给定 n=6，首条 ≥17:09 的模拟概率 | **0.008** |

> ⭐⭐⭐ **所以两个结论方向相反，必须一起说：**
> **①「低量日普遍启动更晚」是次序统计量假象，无解释力**（本来我差点当成发现写下去）
> **② 08-12 的晚启动扣掉低量效应之后仍然异常（p≈0.008），所以那天确实有别的原因，而不只是「发得少所以看起来晚」**
> ⭐⭐ **这恰好是我这两周在 HF/tech-blogs 反复记的那条方法学的自我应用**：[[research-notes/2026-08-13-hf-daily-papers-aug12-13]] 里 VibeLifeBench 的 within-task σ=10.0 让 12 分的模型差距接近无意义、Evo-Bench 因分不清 2.2 分噪声底而丢掉最好的 harness、以及 [[tech-blogs/2026-W33d]] 那条「优化一个固定度量就会把它打坏」。**我今天对自己的观察做了一次 adversarial verify，它杀掉了主张的一半、并把另一半的置信度提高了**——因为第 ③ 步的 p=0.008 是**在控制住已知机械效应之后**得到的，比第 ① 步那个未控制的 p=0.0039 可信得多。
> ⭐ **可复用的判据（值得记住）：当一个相关性的两个变量里有一个是「某个集合的极值」时，先算次序统计量零假设，再谈显著性。**
## Open Questions

1. ⭐⭐ **08-12 那天的晚启动（扣掉低量效应后 p≈0.008）到底是什么原因？** 已排除「因为发得少」。剩下的候选：内部发布流程当天延后 / 某个大发布挤占了排期 / 单纯的偶发。⚠️ **我手上的数据不足以区分，且 AWS 不公开发布流程，所以这条可能永远无解**——记录它的目的是防止以后再看到低量日时把它当成同一现象。
2. ⭐⭐ **IAM role manager 的托管模板具体给了什么权限？** 我上面的批评（模板作用域 ≠ 任务作用域）目前是**结构性推断，没有看过任何一个模板的实际内容**。→ 公告说模板可检视、且指向 Security Blog 有长文。**在把这条写进客户材料之前必须先读一个真实模板**，否则就是我自己批评过的「未读正文却长出一句看似合理的判断」。
3. ⭐ **role manager 支持的 6 个控制台是哪 6 个？** 公告只点名 Lambda 与 EventBridge。这决定了上述 blast radius 关切的实际覆盖面。
4. ⚠️ **Quick 的 deny by default 是否覆盖「已存在能力的新版本」？** 公告说「限制某类别也会限制该类别里已存在的能力」，但一个已放行的能力若新增了子能力，算新能力（被拒）还是算已放行？—— 这正是准入闸门最容易漏的缝，公告未答。
5. ⭐ **EKS 的事件保留时长上限是多少？** 若它能被调到足够长，就是 agent 改动集群场景里现成的宿主侧审计窗口；若上限很短，则「用 k8s event 做审计」这条路走不通。未核。
