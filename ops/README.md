## `run-log.tsv` — 心跳日志

由 `scripts/runlog.py` 追加写。每个 recurring digest 任务在**开始时**写一行 `start`、**完成时**写一行 `done`。

```
ts_utc            task         phase  detail
2026-08-19 07:58  hf           start
2026-08-19 08:31  hf           done   window=88 new=12
```

### 为什么是两行而不是一行

2026-08-15~17 三天 HF / Reddit / tech-blogs 零产出，而 `CronList` 显示 6 个任务全在。**「任务在但会话没跑完」与「跑了但确实没内容」在产出上完全一样**，所以那次是几天后才发现的。

⭐⭐⭐ 而那次失效的形态恰恰是**会话跑到一半死掉** —— 只在末尾写一行心跳的话，正是这种情形什么都不写。写 `start` + `done` 两行才能事后区分三个状态：

| 日志形态 | 含义 |
|---|---|
| **完全没有行** | 任务根本没启动（cron 不在了，或会话立刻死） |
| **只有 `start`** | 跑了但没完成 ← **08-15~17 就是这个形状** |
| **`start` + `done`** | 正常 |

### 检查

```bash
uv run python3 scripts/runlog.py check --days 7
```

打印 `RUNLOG OK` 或 `RUNLOG ANOMALY` + 每条发现，**永远 exit 0**（它是信息性的，不能让 digest 跑不下去）。

⭐⭐⭐ **`check` 写进了每一个任务的 cron prompt，而不是只写进最可靠的那个** —— 因为**检测器不能住在被检测对象里**：它会跟着一起消失。08-15~17 那次恰好有一个任务（AWS）活着，而**一个就够了**。

### 它能做到与做不到的

- ✅ **把空缺从 3 天压到 1 天**：任何一个任务在次日跑起来时就会报出前一天的缺失。
- ❌ **不能挽回那一天** —— 空缺的真正代价来自数据源侧：Reddit 的 top-of-week 有 7 天跨度（兜得住），但 **tech-blogs 最浅的几个 feed 深度不足一天**（2026-08-18 实测：arXiv cs.AI 只有「当天那一批」、LessWrong 0.26 天、量子位 1.75 天）⟹ **那一天的这几个 source 无论何时发现都已经没了。** 心跳的价值在于**不让它连续发生**。
- ⚠️⚠️ **只对已观测的日子下断言，而观测起点是「按任务」的** —— `check` 打印的 `observed: <task> since <date>` 就是每个任务自己的第一行日期，早于它的日子一律不报；从未写过任何行的任务单独列在 `not yet under observation` 里，**而不是报成漏跑**。
  - ⭐⭐⭐ 这一点是建完之后立刻改掉的一个 bug：第一版用**全局**最早日期作起点，于是「明天」会把今天的 hf/reddit/tech-blogs 报成 `NO RUN` —— 它们**确实跑了**，只是跑在心跳存在之前。⟹ **第一次真实运行就误报，而误报最坏的时机就是第一次（它会教人忽略这个输出）。**
  - ⭐⭐ **这与 `aws_whats_new.py` 里「算回填延迟下界必须用那次运行真正拥有的窗口」是同一条纪律，也是同一个错误形态：不能对自己没有观测的区间断言缺失。** 两处都是我先写了一个偏向「看起来更有问题/更安全」的版本，再靠一个具体反例发现的。
  - ⭐ 改完后测了四条回归，其中第三条最要紧：**观测起点之后真的漏了一天时必须仍然报出来** —— 只测「误报消失了」看不出正常路径有没有被一起关掉。
