# Ontology、Taxonomy、知识图谱与 GraphRAG：概念、选型和落地调研

调研日期：2026 年 10 月 22 日  
适用场景：企业文档、技术研究资料、产品与服务知识库  
报告性质：一手资料核实与工程方案建议；不是已经运行过的产品评测

## 0. 范围与阅读方式

本报告将前文的“Onto”和“taxon”按 **Ontology（本体）** 与 **Taxonomy（分类体系）** 理解；范围限定为知识组织与知识系统，不讨论生物分类。

用户尚未给出业务领域、数据量、权限要求、预算和现有技术栈，因此以下以“用企业文档回答技术与产品问题”为假设场景。路线、规模和验收阈值都是建议，需要用真实问题集修订，不代表已经验证的收益。

文中标注 `[Sxx]` 的内容可追溯到文末一手来源；标明“建议”的部分是基于这些资料形成的工程判断。对于项目文档和默认分支，本次核实只能说明调研时网页描述的能力，不能替代固定版本后的实际测试。

## 1. 执行摘要

**结论：这些技术不是互相替代的产品，而是知识系统的不同层。不要先建一个覆盖全公司的大本体，再期待问答自然变好。**

建议按以下顺序推进：

1. **先定义真实问题和验收集。** 区分查原文、关系查询、全库归纳和执行业务动作。
2. **建立可追溯的文档层。** 保留原文、版本、片段位置、来源和权限。
3. **并行建立小词表与轻量领域模型。** 只定义当前问题必需的分类、实体、关系和规则。
4. **先测关键词＋向量的混合检索。** 作为对照组，不预设知识图谱一定能提升效果。
5. **对关系密集型问题增加小图谱。** 例如依赖链、产品版本差异、组织关系、影响范围。
6. **对全库归纳单独评测社区型 GraphRAG。** 不把它默认装进所有问答请求。
7. **需要正式语义互操作或逻辑推理时，再投入 RDF/OWL。** 需要结构校验时则配置约束验证，不能混为一谈。

这里的先后是降低验证成本的建议，不是必须执行的标准流水线。例如已有可靠业务数据库且目标是影响分析，可以直接以业务关系图为起点；只有文档检索需求的系统，也可以长期不建图谱。

## 2. 概念地图：每个东西到底管什么

| 概念 | 核心问题 | 典型内容 | 不应误认为 |
|---|---|---|---|
| Taxonomy | 信息如何分类、导航、统一术语？ | 类别、上位/下位关系、标签、同义词 | 完整的业务语义模型 |
| Ontology | 领域中有哪些概念、关系、属性和约束？ | 类、关系、规则；某些本体也包含实例 | 必须是 OWL 文件，或只能有抽象概念 |
| Knowledge Graph | 哪些具体对象具有哪些关系？ | 实体、关系、属性、来源，有时还包含模式层 | 必须事先有一个完整正式本体 |
| 图数据库 | 怎样存储、索引、查询图结构？ | 属性图或 RDF 数据、查询引擎 | 图谱中的事实天然可信 |
| 向量索引 | 哪些内容在表示空间中相近？ | 文本或对象的向量及元数据 | 定义了“属于”“依赖”等业务语义 |
| RAG | 回答前怎样取回外部证据？ | 检索、重排、上下文组织、生成 | 一定只用向量，或天然不产生错误 |
| GraphRAG | 图结构如何参与检索或证据组织？ | 实体检索、路径扩展、社区摘要等 | 只有一种固定实现 |
| Agent | 如何编排检索、工具调用和行动？ | 计划、执行、状态、工具权限 | 是另一个知识存储格式 |

表中标准相关区分依据 W3C 的 SKOS、OWL 和 RDF 定义；属性图、向量索引与混合检索的实现依据官方产品资料。[S01] [S02] [S04] [S06] [S08] [S09]

**建议采用的理解：Taxonomy 是组织词汇与概念的视角；Ontology 是语义建模的视角；知识图谱是承载对象及关系的知识表示；RAG 是使用这些知识回答问题的流程。**

它们可以相互结合，但不是必须依次经过的四个阶段。一张知识图谱可以同时含分类关系、领域模式和实例；一个本体也可能独立于图数据库存在。[S01] [S02] [S04]

## 3. Taxonomy 与 Ontology：关键差别和常见误区

### 3.1 Taxonomy：先解决分类和术语一致性

以技术知识库为例，分类可以包括“推理技术—量化—低比特量化”，并为同一个概念维护中文名称、英文名称和别名。SKOS 提供首选标签、替代标签、broader、narrower、related 等表达方式，适合词表、分类体系和主题体系。[S01]

需要注意：

- 分类体系可以有多重上位关系，不必局限于单父节点的树。
- SKOS 的 `broader` 不能一概当成 OWL 的类继承；`broaderTransitive` 才是相应传递关系，直接 `broader` 关系本身并未声明为传递属性。
- “更宽泛的主题”“是某类”“是某实例”“是某对象的一部分”，是不同关系。

这些区分直接影响查询和推理结果。[S01] [S02]

**建议：** 对搜索过滤、标签统一、目录导航，先用轻量分类词表即可。每个概念至少保留稳定 ID、首选名、别名、说明、上位概念、负责人和版本。不必为了做目录引入完整 OWL 推理。

### 3.2 Ontology：明确关系含义，而不只是把节点连起来

假设领域中有“产品”“版本”“能力”“机构”“文档”，本体或领域模型需要进一步明确：

- “产品有版本”与“机构发布产品”是两种不同关系。
- “某版本支持某能力”必须注明版本、环境或条件。
- “文档提到某产品”不等于“产品具备文档中出现的所有能力”。
- 同一个对象的别名与两个相似对象，不是同一种情况。

正式 OWL 本体可以定义类、公理、属性以及用于推理的语义；工程上也可先采用受控的 JSON/YAML 模式或关系类型表，但后者并不自动拥有 OWL 的形式语义。[S02]

### 3.3 OWL 不等于数据库校验器

OWL 采用开放世界语义：没有记录一个事实，不代表该事实为假。属性的 domain/range 还可能用于推导类型，而不是像数据库字段约束那样简单拒绝不合格数据。OWL 也不默认采用“不同名称必然代表不同对象”的假设。[S02] [S16]

例如，定义“`worksFor` 的主体是员工”，在 OWL 中可能让系统推导出该主体是员工，而不是以“输入对象没有员工标签”为由直接拒绝它。

如果目标是检查“每个版本必须有版本号”“日期必须是日期类型”“关系对象必须满足指定形状”，SHACL 更贴近 RDF 图的约束验证需求。SHACL 校验与 OWL 推理可以配合，但不应相互替代。[S03]

**建议分成三项实现：**

1. 语义定义：实体与关系究竟意味着什么。
2. 入库验证：数据是否满足当前应用规定的格式和约束。
3. 推理规则：允许产生哪些派生结论。

“格式合法”“逻辑一致”“有现实证据”是三道不同的检查。

## 4. 知识图谱不是图数据库，也不等于模型抽取结果

RDF 以主语、谓语、宾语三元组表达关系；属性图则常用带标签、属性的节点和带类型、属性的关系。两者都能承载领域关系，但数据模型、标识方式和查询生态不同。Neo4j 的属性图不是自动带有 RDF/OWL 语义；RDF 三元组本身也不代表系统已经配置推理器。[S04] [S06]

**工程建议：把图谱分为三个信任层。**

| 层 | 内容 | 是否可直接当成答案中的事实 |
|---|---|---|
| 候选层 | LLM 提取的实体、关系、同名对象合并建议 | 否，应验证和去重 |
| 断言层 | 有来源、版本、适用范围，且通过规则或审核的陈述 | 可以作为有出处的陈述，仍需判断来源可信度 |
| 派生层 | 规则推导、统计归纳、模型摘要 | 必须标注推导依据与性质 |

候选关系“产品 A 支持能力 B”，至少应该能够回答：哪份资料说的、哪个版本、在什么环境下成立、谁核实的。没有这些信息，连线再漂亮也不宜进入生产答案。

### 4.1 长期知识资产与检索索引要分开

建议区分两类图：

- **领域事实图：** 明确身份、来源、权限、生命周期，供多个业务长期使用。
- **检索图或摘要图：** 为某种检索方法生成的实体关联、社区、摘要，可以重建。

这样，替换一个检索算法不会改写业务事实。尤其不要把模型生成的社区报告直接升级成已核实的领域断言。

## 5. 现在的路线：RAG、GraphRAG、时序记忆与业务 Ontology

### 5.1 混合 RAG：多数文档型场景值得先做的基线

关键词检索擅长精确名称、编号等词项匹配，向量检索用于语义相似检索；混合检索将两类结果结合。Azure AI Search 的官方实现并行执行文本和向量查询，并以 RRF 合并结果；具体系统是否使用这一实现取决于所选引擎。[S09]

**建议：** 对“手册在哪里写了某限制”“某版本的参数是什么”，先测混合检索、元数据过滤与重排。分类词表可以辅助扩展别名或过滤，但展开词表后仍要验证是否增加了误召回。

### 5.2 图增强检索：给关系问题增加结构化证据

这里使用“图增强检索”指一种工程模式：先定位对象，再沿明确关系查询或扩展，取回相关原文，最后生成答案。

例如“某组件变更会影响哪些服务”可以先查服务—组件依赖，再取回每条依赖的来源。此类路径的好坏，取决于身份解析、关系准确度、方向、版本和范围，而不只是生成模型能力。

**建议：** 从预定义的一至两跳关系查询做起，设置类型白名单、时间过滤、结果上限和证据要求。复杂多跳路径必须单独测试，不让 Agent 无限制遍历。

### 5.3 Microsoft GraphRAG：适合按问题类型评测，而不是默认开启

Microsoft GraphRAG 的标准索引流程从文本单元提取实体与关系，建立社区层次并生成社区报告。查询侧包括 Local、Global、DRIFT 和 Basic 等方式：Local 结合实体邻域及文本证据；Global 主要利用社区报告进行全局综合；DRIFT 结合社区信息和局部探索；Basic 提供向量检索基线。[S13] [S14]

因此，“整个资料库有哪些主要主题和分歧”与“某产品在某版本是否支持某能力”不应使用同一套默认策略。GraphRAG 的社区摘要并不自动等于正式本体，也不保证结构化关系已经完整、精确或可直接用于业务统计。

增量更新需要特别小心：本次所读默认源码按文档 `title` 集合计算差异，入口仅返回 `new_inputs`。因此，同名文档正文改写不会作为新增输入处理；计算了删除集合也不代表入口执行了删除传播。社区与报告合并采用编号映射后追加，不能据此认定会对全库重聚类或与全量重建一致。这些结论限定于所核查的默认路径，不是对所有定制部署的判断。[S15] [S21] [S22]

官方另外提供 Fast 索引路径，使用 NLP 名词短语与共现等方式减少 LLM 抽取；图中关系的含义与标准路径不完全相同，默认语言处理也不能直接视为已验证中文效果。选择“更快的图”之前，需要先比较它是否保留了业务需要的关系语义。[S24]

调研时仓库 README 还声明：项目主要处于维护状态，不接受新 PR 或实现新功能，并视情况修复缺陷、更新依赖；并非微软正式支持的产品。生产选型需据此评估自维护、锁定版本和替换成本，不能把研究项目当作有商业服务承诺的托管产品。[S23]

**建议：** 用同一问题集比较“混合检索”“实体图扩展”“社区型 GraphRAG”，分别测精确查证、关系查询、全局归纳；记录索引成本、更新时间和回答成本，不只比较回答是否更长。详细核实与 LazyGraphRAG 实验边界见 [GraphRAG 一手资料核实附录](2026-10-22_GraphRAG_一手资料核实.md)。

### 5.4 LightRAG 与 Graphiti：关注能力类别，不按项目名选型

LightRAG 的官方项目提供以实体/关系图结合检索的框架与不同查询模式；Graphiti 的官方项目强调持续更新、时序关系及混合检索，面向动态知识与 Agent 记忆等用途。这些是项目描述的能力，不是本报告已经验证的性能结果。[S17] [S18]

**建议：** 若问题是“最近发生了什么、当时关系是什么”，优先评测时间建模和更新语义；若问题是“静态资料库里怎么取证”，优先评测检索和引用准确度。不要仅因一个项目叫 memory，就把长期业务知识全部托管给它。

不使用不同论文或 README 中的异构基准做性能排名。本次没有实际复现这些框架，也没有固定其依赖与发布版本。

### 5.5 Palantir 语境的 Ontology：还包含业务行动

Palantir 官方把 Ontology 描述为覆盖对象、关系及行动等的业务运营层，并强调与数据、模型和应用衔接。它不应被简单等同于 W3C OWL 文件或一组分类标签。[S19]

**建议：** 如果需求进一步变成“批准变更、创建工单、修改业务状态”，需要新增动作权限、审批、幂等、审计和失败恢复。只读知识问答与可执行业务操作应当是两种不同授权等级，不能因为图谱查询成功就允许写操作。

## 6. 决策表：什么问题值得用什么

以下是选型建议，不是保证效果的结论。

| 主要问题 | 建议起点 | 图谱何时值得增加 | 常见误选 |
|---|---|---|---|
| 找段落、手册、编号、原话 | 关键词＋向量＋元数据过滤 | 名称歧义或跨文档对象整合明显影响检索 | 一开始就建复杂本体 |
| 标签统一、专题导航 | Taxonomy／受控词表 | 需要导航之外的对象关系 | 为每个词都创建业务实体 |
| 依赖分析、影响范围、组织关系 | 业务关系数据＋关系图查询 | 图结构就是主要问题结构 | 仅用相似度猜关系 |
| 产品版本或能力对比 | 实体／版本／陈述＋原文证据 | 同对象跨文档整合是核心困难 | 把不同版本事实合并到产品节点 |
| 资料库整体主题与观点综合 | 基线 RAG＋社区型 GraphRAG 对照实验 | 基线确实无法覆盖分散证据 | 把社区摘要当完整统计 |
| 精确计数、财务汇总、全量清单 | 权威结构化数据与确定性查询 | 图能表达所需连接条件 | 让 LLM 从摘要里猜数量 |
| 合规规则、跨组织语义互操作 | 明确语义标准；按需 RDF/OWL/SHACL | 多系统需共享概念与规则 | 认为有 JSON Schema 就具备正式本体推理 |
| 持续事件、历史状态、Agent 记忆 | 事件与时间模型 | 历史关系查询、更新频繁 | 只保留最新状态，无法回答历史问题 |

一个实用判断标准：**如果去掉实体身份和关系路径后，问题依然能由几段原文回答，图谱可能不是第一优先级；如果答案本身是一条路径或一个精确对象集合，图谱更值得评测。**

## 7. 推荐架构：三层分工，而不是所有数据都放进图里

以下为参考架构建议。

### 7.1 证据与生命周期层

保留原始资料、清洗版本、文档哈希、来源地址、抓取时间、发布版本、片段与原文位置，以及访问权限。

原文是查证依据；图和向量索引是组织、检索手段。PROV 的实体、活动、代理等概念可用于规范记录数据来源和处理过程，但是否实现成 PROV-O 取决于互操作需求。[S05]

### 7.2 语义与结构层

维护分类词表、受控实体类型、关系定义、实体身份、候选陈述、证据和审核状态。若采用 RDF，额外配置必要的 SHACL 验证；若采用关系数据库或属性图，则实现对应的应用级验证。[S03]

### 7.3 检索与回答层

建议按问题类型路由：

1. 精确查证：关键词／向量召回，按版本和权限过滤，重排原文。
2. 关系问题：先解析实体身份，再执行受限图查询，返回关系及其来源。
3. 全局归纳：使用获准语料的分层摘要或社区报告，必要时回查原文。
4. 结构化统计：直接查询权威数据，LLM 只解释结果，不负责猜计数。

输出时区分“原文明确陈述”“多个来源综合”“规则推导”“尚无足够证据”。引用应支持紧邻的结论，不应只在答案最后放几份相关文档。

## 8. 一个可启动的轻量领域模型

以下模型是针对假设场景的建议，不是通用行业本体。

### 8.1 先定义九类对象

| 类型 | 作用 | 身份与版本原则 |
|---|---|---|
| `Product` | 产品或项目 | 稳定 ID，名称不是唯一主键 |
| `ProductRelease` | 产品的特定发布版本 | 必须与产品及明确版本关联 |
| `Capability` | 能力或特性 | 受控定义，区别同名不同含义 |
| `Organization` | 发布或维护机构 | 别名与组织变化单独处理 |
| `Document` | 逻辑文档 | 不与某次抓取混为一体 |
| `DocumentVersion` | 文档的某个快照 | 内容哈希、获取时间、版本信息 |
| `Chunk` | 可检索文本片段 | 必须关联快照与原文定位 |
| `Claim` | 可审核的陈述 | 主体、谓词、客体、条件、状态 |
| `Evidence` | 支持或反驳陈述的证据 | 引文、位置、来源和审核记录 |

分类目录可单独维护 `Concept` 词表，不必把所有类别都变成产品实体。

### 8.2 先定义少量、含义明确的关系

- `ProductRelease releaseOf Product`
- `Organization maintains Product`
- `DocumentVersion versionOf Document`
- `Chunk partOf DocumentVersion`
- `Claim hasEvidence Evidence`
- `Evidence locatedIn Chunk`
- `DocumentVersion describes ProductRelease`

“某版本支持某能力”先保存为带条件和证据的 `Claim`；通过审核后，可以物化为便于检索的 `supports` 关系，但原始陈述和证据仍应保留。这样不会因一条便捷边丢失版本、条件与争议信息。

### 8.3 示例：区分抽取候选与已核实事实

下面是虚构数据，仅演示结构：

```json
{
  "claim_id": "claim-demo-001",
  "subject_id": "release-demo-2.1",
  "predicate": "supports",
  "object_id": "capability-demo-batch-inference",
  "conditions": {
    "deployment_mode": "self_hosted",
    "operating_system": "linux"
  },
  "status": "candidate",
  "valid_from": null,
  "valid_to": null,
  "observed_at": "2026-10-22T00:00:00Z",
  "evidence": [
    {
      "document_version_id": "doc-demo-v3",
      "chunk_id": "chunk-demo-007",
      "quote": "2.1 版在 Linux 自托管环境中支持批量推理。",
      "locator": {
        "section": "部署支持",
        "paragraph": 2
      }
    }
  ]
}
```

建议区分：

- `valid_from/valid_to`：业务事实何时成立。
- `observed_at`：系统何时见到该陈述。
- 文档发布时间、抓取时间：资料自己的时间信息。

不知道事实有效期时保留未知，不要用抓取时间代替。文档没有提及某能力，只能标为“未找到支持证据”，不能直接变成“不支持”。

## 9. 从文档到可用知识图谱：实施步骤

### 第一步：用问题反推模型

先收集建议数量为 60—100 个真实问题，至少覆盖：

- 精确查证；
- 同名对象辨别；
- 产品版本与条件；
- 两跳关系与跨文档证据；
- 全库主题归纳；
- 证据不足、相互矛盾、权限不足。

数量是启动建议，不是统计充分性保证。每个问题都要说明“什么答案算正确”，并记录权威来源。以此形成 competency questions，即模型需要能够回答的问题。

### 第二步：规范接入和片段定位

建议为每次接入生成文档快照，并保存解析器版本与位置映射。PDF 页码、网页标题和段落位置，可能与清洗后的字符串偏移不同；引用定位必须测试，不能只把清洗文本中的字符位置当成原文页码。

切片时保留标题、表格表头和适用范围，避免将“仅某环境支持”中的限定条件切走。初始切片大小应通过检索效果决定，不在报告中给出对所有数据都成立的固定值。

### 第三步：受控抽取，不让模型自由发明模式

建议向模型提供明确的类型、谓词、含义、允许条件字段和输出格式，并要求：

1. 只提取片段明确表达的陈述。
2. 每条陈述附准确引用，校验引用能定位到来源。
3. 保留版本、时间、单位、否定和条件。
4. 对无法消歧的对象返回候选，不自动合并。
5. 将推测和明确事实分开，不以模型自报置信度直接批准入库。

结构化输出通过只说明格式满足要求；它不说明关系真实，也不说明引用足以支持关系。

### 第四步：实体解析与合并审核

建议采用“确定标识优先，规则与候选匹配补充”：

- 权威主键、规范 URL、注册标识、明确版本号优先。
- 名称归一化和别名表用于产生匹配候选。
- 向量相似度用于辅助筛选，不直接证明两个对象是同一对象。
- 高影响合并需要人工确认，并保存合并前后映射和回滚记录。

在 OWL 中，`sameAs` 表示身份相同，不能轻率用它代替“名字接近”“概念相似”或“两个词表之间有对应关系”。SKOS 的映射关系与 OWL 身份相等并不相同。[S01] [S16]

### 第五步：验证、审核与发布

建议验证四类问题：

1. 结构：字段、类型、主外键、引用位置是否有效。
2. 语义：谓词是否使用正确、类型是否合理。
3. 证据：引用是否真的表达该陈述。
4. 业务：版本、条件、权威级别、冲突状态是否正确。

对来源冲突，应保留各自陈述与来源，不简单投票覆盖；先确定权威来源、适用时间及范围。人工审核优先投向高影响、低确定性的事实。

### 第六步：构建可重建的检索索引

发布受控陈述后再构建向量索引、图邻接索引和必要的摘要。每个派生对象记录输入依赖与生成版本；分类、本体或抽取提示变化时，应能判断哪些对象需要重建。

## 10. 更新、删除与权限：必须在 PoC 中验证

以下为设计和测试要求，不是某个框架已经全部提供的保证。

### 10.1 更新与冲突

不要只“追加新边”。新文档可能纠正旧文档，产品升级也可能使旧关系只对历史版本成立。建议区分新增、内容修订、明确撤销、时间失效，以及来源冲突。

为每条陈述记录状态与版本；为派生边和摘要保存输入依赖。更新时重算受影响部分，并保留可以解释历史答案的记录。

### 10.2 删除与失效传播

删除一个文档的内容后，应检查与之关联的片段、向量、证据、独占支持的陈述、派生边、摘要和回答缓存。

若同一陈述还有其他有效来源，不应误删整个事实；应撤销对应证据并重新判断陈述状态。对隐私或合规删除，不应为了历史可复现继续保留禁止保留的正文，可按政策留最小审计信息。

### 10.3 权限不是只在回答末尾过滤

建议对原文召回、图扩展、证据回查、摘要读取和缓存命中都执行授权检查。注意三个泄露途径：

- 节点或关系的存在本身可能泄露敏感业务信息。
- 跨权限混合生成的社区摘要可能泄露用户看不到的文档。
- 缓存可能将高权限回答提供给低权限用户。

多租户场景建议先隔离索引和摘要，或证明过滤策略覆盖全部检索路径。身份信息、文档 ACL 和授权规则来自可信系统，不能接受源文档正文自己声明权限。

### 10.4 文档内容属于不可信输入

OWASP 将隐藏在网页、文档等外部内容中的指令作为间接提示注入风险的一部分，并说明没有单一完美防线。[S20]

建议将证据文本与系统指令分离；对 Agent 使用只读账号、查询模板、路径限制、资源上限与审计。即使后续允许 LLM 生成图查询，也必须在执行前做解析、权限和操作类型校验，不能仅靠提示词禁止写操作。

## 11. 技术选型：三条路线足够启动

下面是参考方案，不是“最佳产品”排名，也不包含未经核实的价格、规模上限和性能倍率。

| 路线 | 参考组件 | 适用判断 | 需要警惕 |
|---|---|---|---|
| A：关系库＋混合检索 | PostgreSQL；全文检索；pgvector；实体与关系表 | 先做问答、小规模受控关系，团队已有 SQL 能力 | 不要假装关系表自动拥有复杂图算法或正式本体语义 |
| B：属性图＋检索 | Neo4j＋原文存储＋关键词／向量检索 | 路径查询、依赖分析、对象浏览是核心能力 | 关系准确性和原文引用需要应用自己保证 |
| C：语义网栈 | Protégé＋RDF/OWL；Jena Fuseki；SHACL 验证 | 语义互操作、共享标识、正式约束／推理需求明确 | 不要为普通文档问答过早增加建模与推理复杂度 |

官方能力依据：pgvector 支持 PostgreSQL 内的向量相似度检索，并说明可与全文检索结合；Neo4j 使用属性图；Fuseki 提供 SPARQL 服务；Protégé 用于本体编辑。RDFLib 和 pySHACL 可分别作为 Python 侧 RDF 处理和 SHACL 验证工具，但不能据此推断它们适合所有生产规模。[S06] [S07] [S08] [S10] [S11] [S12]

**默认建议：** 在没有更多业务信息前，采用 A 建立基线；若真实问题大量涉及关系路径，采用或增加 B；若有明确的语义互操作和推理要求，再考虑 C。这些路线可以组合，而不是必须迁移全部数据。

Microsoft GraphRAG、LightRAG、Graphiti 更应视为需要评测的检索／知识处理框架或服务层，不要仅因引入其中一个框架就放弃原文层、事实状态、权限模型和审计。

PoC 结束前固定组件版本、许可证、部署模式、备份恢复方式和数据迁移方案；本报告不提供当前云服务价格估算。

## 12. 如何验收：证明图谱有用，而不是只证明图能画出来

### 12.1 三组对照

建议保持文档版本、问题集、生成模型、回答格式和权限条件一致，比较：

- A：关键词＋向量＋重排＋原文引用。
- B：A＋受控实体解析和图关系扩展。
- C：社区型 GraphRAG 或其他全局检索策略。

调参与最终评测使用不同问题；若方法必须使用不同上下文预算，则报告质量与成本之间的折中，不将其伪装成同成本比较。对有随机性的流程重复运行并报告波动。

### 12.2 指标分层记录

| 层面 | 建议指标 | 评估要点 |
|---|---|---|
| 抽取 | 实体／关系精确率与召回率、条件保留率 | 不只看 JSON 是否通过 |
| 身份 | 错误合并率、错误拆分率 | 高影响身份错误单独列出 |
| 检索 | 证据 Recall@k、重排指标、有效路径比例 | 区分对象找对与证据找对 |
| 回答 | 正确性、引用支持率、版本适配、拒答合理性 | 引用可访问不等于引用支持结论 |
| 运维 | 更新／删除正确性、权限隔离、重建时间 | 故障与边界场景必须覆盖 |
| 成本 | 索引成本、人工审核、单次查询成本、P50/P95 延迟 | 不只计生成模型 token |

对于开放式全库归纳，可由领域人员按覆盖度、证据和遗漏评分；对于可结构化回答的问题，优先用确定性答案核对。LLM 评审可辅助，但不要把同一模型的自评当成唯一真值。

### 12.3 建议的启动门槛

以下数字是为了启动讨论的**建议阈值**，不是文献证实的行业标准：

- 核心已发布陈述的来源和版本字段完整率为 100%。
- 验收集中授权绕过和禁止保留内容的删除残留为 0；通过测试不等于已经证明没有所有安全漏洞。
- 关键关系的抽样精确率目标可先设为 ≥95%，同时报告样本量和误差范围；高风险场景需更严格。
- 图增强是否保留，由关系类问题的真实改善、额外延迟和总成本共同决定。
- 全局归纳改善不能掩盖精确查证题上的退化；必要时按题型路由而不是强行统一。

若样本太小、来源标注有争议，不能凭一个百分比宣布系统可上线。

### 12.4 成本核算方式

建议分别计量：

```text
离线成本 = 解析/OCR + 抽取 + 向量化 + 社区/摘要生成
         + 校验与人工审核 + 存储/索引 + 更新/删除/重建

在线成本 = 路由与对象解析 + 检索 + 图扩展 + 重排
         + 证据回查 + 生成 + 监控与审计
```

用真实文档量、变更频率、查询量和当时的报价计算。不在没有样本时宣称“知识图谱更便宜”或“GraphRAG 一定更贵多少倍”。

## 13. 六周试点计划

这是对“数据可访问、约一名工程人员＋领域人员参与”的计划估计，不是交付承诺。建议先选 200—500 份代表性资料，而非随机全量导入；数量只是便于控制试点范围。

| 时间 | 主要工作 | 交付物与决策点 |
|---|---|---|
| 第 1 周 | 选择领域、问题集、来源、权限；识别版本与实体歧义 | 问题及答案标准；初始词表／模型；数据清单 |
| 第 2 周 | 原文版本管理、切片、混合检索、引用定位 | 基线回答；检索与引用问题清单 |
| 第 3 周 | 受控实体／陈述抽取、身份解析、审核界面或流程 | 小事实图；误抽取与误合并报告 |
| 第 4 周 | 关系查询、问题路由、对照评测 | 证明哪些题型有收益；决定保留或缩减图谱 |
| 第 5 周 | 按需评测社区型 GraphRAG；补时间与冲突处理 | 全局问题报告；索引与查询成本 |
| 第 6 周 | 更新、删除、权限、重建、故障测试 | 验收结果；继续投入／只保留基线／停止的决定 |

如果第 2 周基线已经满足大部分需求，先收缩后续范围；如果第 3 周实体身份无法可靠解决，不继续扩大关系抽取量；如果第 5 周摘要带来的收益不能抵消维护和更新代价，保留更简单的检索路线。

## 14. 最容易踩的十个坑

以下是本报告的风险判断与对应建议：

1. **把分类层级当成所有关系。** 明确区分 subclass、instance、part-of、depends-on、mentions。
2. **把相似度当身份或事实。** 相似度用于召回，身份与事实需要标识和证据。
3. **把 LLM 抽取直接发布。** 先保留候选，再验证、消歧与审核。
4. **把缺失当否定。** “未找到”与“不存在”“不支持”分别处理。
5. **把产品与版本混成一个节点。** 条件、环境和时间必须保留。
6. **把社区摘要当权威事实。** 回到原文，区分摘要与经审核陈述。
7. **只设计新增，不设计撤销。** 把更新、删除和派生失效作为同等重要流程。
8. **把权限留到答案末尾。** 所有检索、遍历、摘要和缓存路径都要授权。
9. **由 Agent 自由生成并执行任意查询。** 采用受限、可审计的执行边界。
10. **模型画得复杂，评测却没有基线。** 用真实题型、证据、时间和成本决定复杂度。

## 15. 具体“该怎么搞”：从明天可以做的事开始

建议启动时只做以下六件事：

1. 选一个窄领域，比如“某一类产品的版本、部署条件与能力”，不要从全部企业知识开始。
2. 写出 20 个优先问题，其中至少 5 个必须依赖明确关系或跨文档整合；这 20 个是后续完整问题集的种子。
3. 整理一批权威原文，记录版本、来源、权限；先确保引用可定位。
4. 写一页词表与实体／关系定义，采用第 8 节模型的必要子集。
5. 做混合检索基线，再挑关系题加入图扩展，用相同答案标准比较。
6. 同时验证一例文档改写、一例删除、一例冲突、一例同名对象、一例越权请求。

**最终推荐：轻量 Taxonomy＋问题驱动的领域模型＋带证据的小图谱＋按题型路由的检索。**

正式 OWL、社区型 GraphRAG、时序记忆和业务动作层，是有明确需求才加入的能力，不是所有项目的入场券。下一步要细化部署方案，只需补齐五个参数：业务领域、资料规模与类型、首要问题、权限/更新要求、现有技术栈与预算。
