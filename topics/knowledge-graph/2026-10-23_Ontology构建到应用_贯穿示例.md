# 贯穿示例：从本体构建到服务依赖查询、RAG 与变更 Agent

日期：2026-10-23  
用途：用同一案例解释各层职责，作为实施讨论的起点。  
重要边界：对象、事实与 API 均为虚构；示例片段未在 RDF／SHACL／OWL 引擎执行，不是已验证的生产实现。当前工作环境没有预装 RDFLib、pySHACL 和 owlrl，本次没有安装依赖或启动服务。

## 1. 先定义问题，不先选数据库

假设管理“订单服务”的发布和依赖，希望回答：

| CQ | 问题 | 什么结果算正确 |
|---|---|---|
| CQ1 | 在指定时刻，生产环境的订单服务 2.1 版依赖什么？ | 仅返回该发布版本、环境和有效期下已批准的陈述 |
| CQ2 | 某依赖陈述依据是什么？ | 返回准确来源、片段和核实状态 |
| CQ3 | 订单服务是不是 System？ | 按明确的类继承语义回答 |
| CQ4 | 缺少版本号或证据的记录能否发布？ | 数据校验失败，不能用 OWL 存在性代替必填检查 |
| CQ5 | 当前用户能否创建生产变更单？ | 由策略和动作服务判断，不能由 LLM 自行授权 |

这张表是示例的需求和验收定义，不是标准规定的通用 CQ 清单。

## 2. 最小模型

| 概念 | 含义 | 为什么分开 |
|---|---|---|
| `System` | 逻辑系统的上位类 | 支持基础类型推导 |
| `Service` | 逻辑业务服务，System 的子类 | 不与某次发布混为一体 |
| `Component` | 逻辑技术组件，System 的子类 | 作为依赖对象 |
| `Release` | 某服务的一次明确发布版本 | 版本变化不覆盖旧事实 |
| `DependencyAssertion` | 某版本在特定环境、时间下的依赖陈述 | 保存关系的适用条件 |
| `Evidence` | 支持陈述的资料片段 | 抽取结果可追溯 |

`Service` 与 `Component` 在这个例子中不声明互斥：一个服务是否也作为组件，要由实际领域定义。不要为了“模型整齐”擅自加不相交公理。

核心关系：Release→Service；DependencyAssertion→Release／Component／Evidence。

## 3. 第一步：写少量本体表达

下面标为 `ontology.ttl` 的代码块是逻辑文件示意，尚未创建或部署这个独立文件。

```turtle
@prefix ex:   <https://example.org/onto-demo/> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

ex:ontology a owl:Ontology ;
    owl:versionInfo "demo-0.1" .

ex:System a owl:Class .
ex:Service a owl:Class ;
    rdfs:subClassOf ex:System .
ex:Component a owl:Class ;
    rdfs:subClassOf ex:System .
ex:Release a owl:Class .
ex:DependencyAssertion a owl:Class .
ex:Evidence a owl:Class .

ex:releaseOf a owl:ObjectProperty ;
    rdfs:domain ex:Release ;
    rdfs:range ex:Service .

ex:forRelease a owl:ObjectProperty ;
    rdfs:domain ex:DependencyAssertion ;
    rdfs:range ex:Release .

ex:targetComponent a owl:ObjectProperty ;
    rdfs:domain ex:DependencyAssertion ;
    rdfs:range ex:Component .

ex:hasEvidence a owl:ObjectProperty ;
    rdfs:domain ex:DependencyAssertion ;
    rdfs:range ex:Evidence .

ex:version a owl:DatatypeProperty ;
    rdfs:domain ex:Release ;
    rdfs:range xsd:string .

ex:environment a owl:DatatypeProperty ;
    rdfs:domain ex:DependencyAssertion ;
    rdfs:range xsd:string .

ex:status a owl:DatatypeProperty ;
    rdfs:domain ex:DependencyAssertion ;
    rdfs:range xsd:string .

ex:validFrom a owl:DatatypeProperty ;
    rdfs:range xsd:dateTime .
ex:validTo a owl:DatatypeProperty ;
    rdfs:range xsd:dateTime .
ex:observedAt a owl:DatatypeProperty ;
    rdfs:range xsd:dateTime .
ex:quote a owl:DatatypeProperty ;
    rdfs:domain ex:Evidence ;
    rdfs:range xsd:string .
ex:locator a owl:DatatypeProperty ;
    rdfs:domain ex:Evidence ;
    rdfs:range xsd:string .
```

本体表达了类、属性和基本公理，不包含“所有输入必须已显式写类型”的数据库式检查。RDFS domain／range 会参与类型推导，必填等应用要求在后续形状中定义。[E1] [E2]

## 4. 第二步：接入数据和证据

假设有一份已人工确认的虚构发布资料：

> 订单服务 2.1 版在生产环境依赖缓存组件，自 2026 年 10 月 20 日起生效。

`data.ttl` 示意：

```turtle
@prefix ex:  <https://example.org/onto-demo/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:orderService a ex:Service .
ex:cacheComponent a ex:Component .

ex:orderRelease21 a ex:Release ;
    ex:releaseOf ex:orderService ;
    ex:version "2.1" .

ex:evidence001 a ex:Evidence ;
    ex:quote "订单服务 2.1 版在生产环境依赖缓存组件，自 2026 年 10 月 20 日起生效。" ;
    ex:locator "虚构发布说明 demo-001，第 2 段" .

ex:dependency001 a ex:DependencyAssertion ;
    ex:forRelease ex:orderRelease21 ;
    ex:targetComponent ex:cacheComponent ;
    ex:environment "production" ;
    ex:status "approved" ;
    ex:validFrom "2026-10-20T00:00:00+08:00"^^xsd:dateTime ;
    ex:observedAt "2026-10-23T09:00:00+08:00"^^xsd:dateTime ;
    ex:hasEvidence ex:evidence001 .
```

本例规定：事实区间为 `[validFrom, validTo)`；没有 `validTo` 表示当前记录未注明结束时间。**这是示例的数据契约，不是 OWL 自动赋予的时间语义。**

`observedAt` 表示系统何时取得该陈述，不用它代替事实开始生效的时间。`approved` 是审核服务写入的状态，不能由来源正文或抽取模型自行赋予。

生产实现还应加文档快照、真实定位、审核人／活动、权限与来源撤销机制。可使用 PROV-O 组织处理来源，但 PROV-O 本身不证明这段资料准确。[E3]

## 5. 第三步：用 SHACL 写数据要求

`shapes.ttl` 示意，只覆盖最小结构，不声称验证所有业务正确性：

```turtle
@prefix ex:  <https://example.org/onto-demo/> .
@prefix sh:  <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:ReleaseShape a sh:NodeShape ;
    sh:targetClass ex:Release ;
    sh:property [
        sh:path ex:releaseOf ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class ex:Service
    ] ;
    sh:property [
        sh:path ex:version ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:string ;
        sh:minLength 1
    ] .

ex:DependencyShape a sh:NodeShape ;
    sh:targetClass ex:DependencyAssertion ;
    sh:property [
        sh:path ex:forRelease ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class ex:Release
    ] ;
    sh:property [
        sh:path ex:targetComponent ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class ex:Component
    ] ;
    sh:property [
        sh:path ex:environment ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:in ( "production" "staging" )
    ] ;
    sh:property [
        sh:path ex:status ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:in ( "candidate" "approved" "revoked" )
    ] ;
    sh:property [
        sh:path ex:validFrom ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:dateTime
    ] ;
    sh:property [
        sh:path ex:validTo ;
        sh:maxCount 1 ;
        sh:datatype xsd:dateTime
    ] ;
    sh:property [
        sh:path ex:hasEvidence ;
        sh:minCount 1 ;
        sh:class ex:Evidence ;
        sh:node ex:EvidenceShape
    ] .

ex:EvidenceShape a sh:NodeShape ;
    sh:targetClass ex:Evidence ;
    sh:property [
        sh:path ex:quote ;
        sh:minCount 1 ;
        sh:datatype xsd:string ;
        sh:minLength 1
    ] ;
    sh:property [
        sh:path ex:locator ;
        sh:minCount 1 ;
        sh:datatype xsd:string ;
        sh:minLength 1
    ] .
```

这里的 `minCount`、`class`、`datatype`、`node` 分别用于数量、类型、数据类型和嵌套形状要求，依据 SHACL。[E4]

本例建议把本体与实例合并为验证时的 data graph，形状单独作为 shapes graph；所用推理配置也应固定。这是输入组织约定，不要求数据库一直采用这种物理组织。

还需另行验证：

- `validTo > validFrom`；
- 引文能否准确定位到文档；
- 引文是否确实支持目标关系；
- 版本号是否与权威发布系统一致；
- `approved` 是否来自合法审核操作；
- 当前用户是否有权读证据。

不能把 `sh:conforms true` 当成这些检查已经全部完成。

## 6. 第四步：演示“推理”和“查询”的区别

### 6.1 一个基础蕴含

根据：

```text
Service subClassOf System
orderService type Service
```

可以在相应 RDFS／OWL 语义下推出：

```text
orderService type System
```

这是类继承的逻辑结果，依据 RDFS；是否被存储引擎显式返回，取决于实际推理或查询配置。[E2]

### 6.2 不启用推理器也可明确写查询路径

如果本体与数据可在同一查询视图中访问，可用 SPARQL 1.1 的 property path 找到具备 System 类层次的对象：

```sparql
PREFIX ex:   <https://example.org/onto-demo/>
PREFIX rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT DISTINCT ?object
WHERE {
  ?object rdf:type/rdfs:subClassOf* ex:System .
}
```

本例中预期返回订单服务和缓存组件。这是显式路径匹配，并不说明引擎能够处理全部 OWL 公理。Property path 语法依据 SPARQL 1.1。[E5]

### 6.3 查询带环境、时间和证据的依赖

```sparql
PREFIX ex:  <https://example.org/onto-demo/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>

SELECT DISTINCT ?claim ?component ?evidence ?quote ?locator
WHERE {
  VALUES ?at {
    "2026-10-23T10:00:00+08:00"^^xsd:dateTime
  }
  ?release ex:releaseOf ex:orderService ;
           ex:version "2.1" .
  ?claim a ex:DependencyAssertion ;
         ex:forRelease ?release ;
         ex:targetComponent ?component ;
         ex:environment "production" ;
         ex:status "approved" ;
         ex:validFrom ?from ;
         ex:hasEvidence ?evidence .
  OPTIONAL { ?claim ex:validTo ?to . }
  ?evidence ex:quote ?quote ;
            ex:locator ?locator .
  FILTER(?from <= ?at)
  FILTER(!BOUND(?to) || ?at < ?to)
}
```

预期取回 `dependency001` 及缓存组件和证据。该预期由本文的数据与查询条件推导，**不是已执行测试结果**。查询不包含授权逻辑，实施时必须在执行前绑定用户可见数据范围。

多跳依赖要确保每一跳都满足同一环境、时间与版本规则；不能把所有陈述投影到一张无条件图后直接遍历。

## 7. 第五步：同一模型怎样连接不同存储

| 路线 | 接法 | 不变的契约 |
|---|---|---|
| RDF 图存储 | 本体、数据、形状和 SPARQL 查询视图 | 身份、关系定义、条件、证据 |
| 虚拟知识图 | 数据保留在来源库，配置本体与关系数据映射 | 相同 CQ 和查询答案标准 |
| 属性图 | 为 Release／DependencyAssertion／Evidence 创建节点与明确关系 | 同样保留版本、时间和审核状态 |

Ontop 提供虚拟图访问，Neo4j 提供属性图模型；这些能力不意味着本例无需适配即可在所有引擎执行。[E6] [E7]

如果属性图里额外物化便捷的“依赖边”，建议保留对应陈述 ID、环境、时间、来源与重建方式；不要因便捷边丢失原来的语义。

## 8. 第六步：供 RAG 使用

建议的只读流程：

1. 把“订单服务 2.1、生产环境”解析为明确对象和条件。
2. 调用受控依赖查询接口，而不是让模型随意选择版本。
3. 取回陈述和原文证据。
4. 检查证据可访问、未被撤销。
5. 让模型解释结果，并标明范围。

示例答案应类似：

> 在示例资料覆盖的范围内，订单服务 2.1 版在生产环境依赖缓存组件。依据是虚构发布说明 demo-001 第 2 段；记录的生效时间为 2026-10-20。没有据此判断其他版本或全部运行依赖。

不应回答“订单服务所有版本都依赖缓存组件”，也不应在没有完整依赖清单时说“唯一依赖是缓存组件”。

这种关系取证流程不要求先生成全库社区报告；是否加入其他 GraphRAG 策略，另用全局问题评测。

## 9. 第七步：供 Agent 创建变更单

动作 API 示意：

```json
{
  "action": "propose_dependency_change",
  "release_id": "orderRelease21",
  "environment": "production",
  "expected_revision": "revision-demo-7",
  "idempotency_key": "change-demo-20261023-001",
  "reason": "请求评估替换缓存组件",
  "evidence_ids": ["evidence001"]
}
```

这表示提出变更，而不是立即修改生产依赖。身份与租户应由可信认证上下文绑定，不让模型在请求里自行声明“我是管理员”。

建议动作服务依次检查：

- 用户是否可见服务、版本、环境和证据；
- 是否具有提出变更的权限；
- 当前版本是否等于预期修订；
- 证据是否仍有效；
- 是否需要另一位负责人批准；
- 重复提交能否返回同一变更单；
- 执行失败如何记录和恢复。

Palantir 的 Action Types 是对象模型连接业务修改的一种产品实例；本例并不要求采用该产品，也不把动作权限当作 OWL 推理结果。[E8]

## 10. 第八步：更新、撤销和权限变化

假设 2.2 版改用另一个组件：

1. 新建 2.2 发布对象，不覆盖 2.1 的身份。
2. 为 2.2 新建带环境与生效时间的依赖陈述。
3. 2.1 的历史陈述不必因此自动消失；是否仍有效要依据生命周期。
4. 如果原资料被纠正，撤销或修订受影响陈述，重新判断派生结果。
5. 若证据因隐私或合规要求删除，按政策删除正文和相关派生内容。
6. 若用户权限改变，使相关索引、摘要与缓存重新授权。

新事实、纠错、历史失效、隐私删除、访问撤销，不能合并成一个“更新节点”操作。

## 11. 最小验收清单

| 测试 | 预期性质 |
|---|---|
| 缺少 `version` | Release 形状应不符合 |
| 依赖陈述缺少证据 | Dependency 形状应不符合 |
| 只有 staging 环境陈述 | production 查询不得返回 |
| 陈述尚未生效／已结束 | 指定时刻查询不得返回 |
| 陈述状态 candidate／revoked | approved 查询不得返回 |
| 名称相同但稳定 ID 不同 | 不自动合并对象 |
| 未找到某依赖 | 返回证据不足，不推出没有依赖 |
| Service 子类 System | 在声明语义下具备 System 蕴含 |
| 来源不可见 | 不返回关系、引文或缓存中的敏感内容 |
| 重复提出变更 | 幂等服务不应重复创建 |
| 版本发生并发变化 | 动作前置条件应失败或要求重新确认 |
| 文档与证据被删除 | 受影响检索、摘要及动作计划重新评估 |

上表是计划验收项，未执行通过。

## 12. 这个案例说明了什么

**Ontology 定义对象与关系；数据与证据承载陈述；SHACL 检查指定结构；推理器计算蕴含；查询选择适用事实；RAG 解释证据；动作服务负责授权和业务修改。**

把这些职责分开以后，才可以根据业务选择哪些环节需要更强的实现，而不是期待一张图或一个大模型自动完成所有事情。
