# Ontology 怎样建立、怎样存储管理、怎样应用

整理日期：2026-10-23。本文用一个产品知识库的例子讲完整过程。例子为虚构，实施步骤是建议；标准与工具能力的出处放在相关段落和文末。

假设公司有几十种软件产品，每种产品有不同版本，产品手册、测试记录和内部数据库都在记录它们的能力。你想回答一个具体问题：

> 哪些产品版本在 Linux 自托管环境下支持批量处理？依据是什么？

这个问题看起来不复杂，却要求系统区分产品与版本、理解“支持”的条件、找到资料来源，并处理资料更新。Ontology 就从这些需要开始建立。

我们下面依次做三件事：把业务概念定义清楚，把定义和具体事实保存起来，再让应用使用它们。正式 OWL 本体也可以包含实例，本文为方便管理把“定义”和“事实”分开讨论，不把这种工程安排当作语言的强制要求。[C01]

## 一、怎样建立 Ontology：过去的方法和现在的方法

### 先走完一个实际构建过程

第一步是写出你希望系统回答的问题。在上面的例子里，除了“哪些版本支持批量处理”，还要问“某产品的最新版本是什么”“两个资料里的名字是否指同一个产品”“一条支持声明在哪份资料里出现”。这些问题限制了模型范围，也可以留作后面的验收题。Stanford 的本体构建方法就是从领域、用途、要回答的问题和复用已有模型开始，再逐步整理术语、类、属性和实例。[C02]

接着拿几份真实资料试着回答这些问题。你很快会发现，“产品 A”和“产品 A 2.1 版”不能放在同一个位置。前者指产品，后者指一次发布；2.1 的能力不一定适用于 2.0。于是先定义“产品”“产品版本”“功能”这几类对象。

然后把关系写清楚。产品版本通过“属于哪个产品”关联产品；某条“支持声明”则关联一个产品版本和一个功能。为什么还要引入支持声明？因为“支持批量处理”有环境和时间条件，还需要来源。把这些信息集中在一条可追溯的声明中，比直接给产品连一条没有条件的“支持”边更容易管理。这是针对本例的建模选择。

用普通话写出来，可以先是这样：

```text
产品版本，关联其所属产品。
支持声明，关联一个产品版本和一个功能。
支持声明，记录部署环境、有效时间和证据。
证据，能定位到某个文档快照中的具体位置。
```

这时候还不用急着选数据库。先让业务人员看懂这些定义，并用真实资料检查：有没有同名不同义？有没有把“手册提到某功能”误当成“产品支持某功能”？版本、环境和来源能否表达完整？

定义通过检查后，再决定用什么方式让软件读取。需要正式逻辑语义时，可以用 OWL 表达类、属性和公理；只需要统一接口与数据处理时，也可以先使用受控类型表或声明式模式。但一个 JSON 或 YAML 文件，不会因为写了类型名称就自动具备 OWL 推理语义。[C01] [C03]

还要把数据质量要求单独写下来。比如“版本号不能为空”“每条已发布支持声明必须有证据”。采用 RDF 时，可以用 SHACL 检查指定数据图是否满足这些要求；采用其他存储时，可实现相应的数据库或应用校验。OWL 公理和必填字段检查是不同工作。[C04] [C05]

最后放入少量样例数据，回头回答第一步的问题。答错了，就检查定义、映射、查询或数据，不要先扩大模型。如果一个问题始终需要人工补充未记录的条件，说明模型或数据接入还没完成。

### 过去是怎么做的

传统人工路线由领域专家与知识工程人员共同完成。专家解释业务中的概念和区别，工程人员把它们整理为类、关系和逻辑表达，再用编辑器维护。Protégé 是这类工具的一个例子：它提供桌面编辑器，也有用于协作的 WebProtégé。[C06]

这条路线的重点在“定义经过讨论”。例如，“最新版本”是发布日期最新、版本号最大，还是当前允许部署的版本？这三种定义可能产生不同答案。人工建模的工作，往往就是把这种分歧提前解决。

大模型之前也已经有半自动方法。规则和自然语言处理可以从文档中找术语、识别句式，再提出分类或关系候选。已有结构化数据还可以通过映射转换成统一知识表示。2012 年发布的 R2RML 就定义了关系数据库到 RDF 的可定制映射；这解决的是数据接入与转换，不会自动替你决定所有业务概念的含义。[C07]

GATE 的旧教程就展示过这类做法：用人工编写的规则提取公司收购关系；TermRaider 则通过语言处理找术语候选、评分，再让人筛选。这些工具减少了找词和找关系的工作，但候选能否进入本体，仍需核实。[C24] [C25]

所以不能把历史写成“过去全靠手写，现在才开始自动化”。不同技术分担的是不同工作：术语提取减少阅读工作，映射减少重复录入，推理帮助检查定义及已有事实。人工仍需要决定候选是否成立。历史工具的补充出处见 [建立方法核实记录](2026-10-23_Ontology建立方法_补充核实.md)。

### 现在多了什么

现在的大模型可以参与更多需要理解语言的工作。你可以让它从产品手册整理术语与别名，根据给定类型抽取对象和陈述，也可以让它提出关系定义、数据映射和测试问题的草稿。

这里要分清两种结果。如果模型提取“产品 A 2.1 在 Linux 下支持批量处理”，得到的是一条候选事实。如果模型提出“应该把产品版本单独建成一类”，得到的是一个模型设计建议。两者都可能有用，但批准方式不同。

OntoGPT 的官方定位是利用 LLM、模式和本体 grounding 从文本提取结构化信息；Schema Automator 则可辅助从已有数据或模式生成声明式模型。不能把这些能力概括为“工具已经自动完成并证明了整个正式本体”。[C08] [C09]

OntoGPT 也可以在预先配置的映射模板下输出 OWL 公理。这种路线把“允许生成什么逻辑结构”交给模板，再由模型从文本抽取内容；它与让模型自主决定整个领域的类体系和公理不同。模板及生成结果也要审核。[C26]

我建议把当前流程安排为：人先定范围与关键概念，工具批量提出候选，业务人员核对定义和高影响事实，再执行结构校验、必要推理和问题回归。模型新提出的类型先进入审核，不应让每份新文档随意改写正式类型。

不同数据也不必使用同一种抽取方法。产品数据库已有可靠主键、版本表和能力记录时，确定性映射通常值得优先评测；手册中的条件和说明，才需要文本抽取。没有必要让大模型重新猜已经清楚记录在数据库里的内容。这是本例的方案建议。

一轮构建结束，应能拿出概念和关系的定义、对象标识规则、数据映射或抽取说明，以及一组带预期答案的测试。是否使用 OWL，要看实际需要哪些逻辑表达和推理。OWL 2 的 EL、QL、RL 等片段服务不同任务，选择时需同时检查引擎支持的范围。[C10]

## 二、怎样存储和管理：RDF、OWL、文件与图数据库分别做什么

### RDF 先解决“数据怎样表达”

RDF 用“主体—关系—客体”三元组表达陈述。例如：

```text
产品A_2.1        属于产品       产品A
支持声明001     对应版本       产品A_2.1
支持声明001     对应功能       批量处理
支持声明001     部署环境       Linux自托管
支持声明001     依据           文档快照007
```

上面是中文示意，不是可直接导入的 RDF 代码。真正的 RDF 使用标识区分对象，使用明确的谓词表示关系；客体也可以是字符串、日期等值。这样，多个来源可以围绕相同标识连接信息。RDF 定义的是数据模型，不是某款数据库。[C11]

本体定义也能表达为 RDF 图。OWL 在此基础上给类、属性和公理规定更丰富的逻辑含义，例如类继承或逆关系。OWL 本体可以交换为 RDF 文档，但把这些表达保存下来，并不等于存储系统已经执行了相应推理。[C12]

如果要保存成文件，Turtle 是一种 RDF 文本写法，常用 `.ttl` 后缀；RDF/XML 等是其他写法。文件格式、知识的逻辑含义和数据库引擎，应分别选择。[C13]

### 小规模模型，可以先以文件为主要交付物

本体定义可以先保存为版本化文件。本文建议将定义、数据形状、来源映射和测试分开维护，例如：

```text
ontology.ttl       概念、关系和必要公理
shapes.ttl         录入和发布时的数据要求
mappings/         现有数据库或资料怎样接入
tests/            样例数据、问题和预期结果
```

这是建议的文件组织方式，不是已经创建的项目。小样例数据可以随测试保存；不断增长的业务事实和原始资料，应根据规模与更新方式选择数据库、对象存储等设施，不能把所有内容都当成本体源码维护。

编辑工具也不等于线上数据库。Protégé 适合编辑和检查定义，线上应用则还需要持久存储、查询接口、访问控制与更新流程。[C06]

### 数据多了，要选择怎样存储或访问

一种路线是 RDF 存储。它按 RDF 数据模型组织知识，通常通过 SPARQL 查询。以 Apache Jena 为例，Fuseki 提供 SPARQL 服务，并可结合 TDB 进行持久存储。适合考虑这条路线的原因，是你需要 RDF 交换、共享标识或标准查询，而不是它的名字里出现了“知识图谱”。[C14] [C15]

另一种路线是 Neo4j 这类属性图。它用节点、带类型的关系，以及节点和关系上的属性表达数据。你可以建立产品、版本、支持声明和证据节点，用关系把它们连接起来。属性图可以承载领域模型，但节点标签和关系类型不自动具有 OWL 公理的全部含义。[C16] [C12]

例如，“产品 A 2.1 是企业版”与“所有企业版都是软件发布版本”同时存在时，是否能自动查询到“软件发布版本”类型，要检查实际查询或推理配置。普通路径查询可以显式处理部分继承关系，但不能因此认定系统完成了全部 OWL 推理。

还有一条容易被忽略的路线：数据仍留在原数据库里。本体定义统一概念，映射说明原表和字段如何对应这些概念，查询时再访问源数据。Ontop 就提供这种虚拟知识图访问，能够把 SPARQL 查询转换成底层 SQL。它说明使用本体不必以全量搬入图数据库为前提。[C17]

因此，RDF 与图数据库不是两个同层的二选一选项。可以用 RDF 模型存入支持它的引擎，也可以将领域模型映射到属性图，还可以通过虚拟访问查询已有数据库。

### 管理工作包括两种版本，以及知识何时失效

“新增产品 A 2.2 版”主要是事实数据变化；“把产品拆成软件产品和硬件产品”则是定义变化。两者需要不同的发布和迁移处理。

本体版本应能说明概念和关系怎样变了，应用使用的是哪一版。OBO 的版本原则要求正式发布版本能够标识、保存并取回原件；这是一个可以借鉴的社区实践，不是所有领域的强制制度。[C18]

具体事实还要记录产品版本、适用环境、生效或失效时间、资料快照和审核状态。PROV-O 提供表达来源与处理过程的词汇；记录了来源以后，仍需核对它是否支持陈述。[C19]

本例中，2.2 版不再支持某功能，不代表 2.1 的历史陈述应该消失。原文如果纠正了 2.1 的说法，就要撤销或修订相应陈述，再检查由它生成的推论、索引、摘要和缓存。

本体修改也一样。假如增加一条类继承或身份相等公理，旧数据的推理结果可能改变。本文建议发布前重新跑问题测试，并固定本体、形状、映射和推理配置的版本。

RDF 可以用 named graphs 将多份图数据分别组织起来。它有助于区分来源或快照，但图名本身不会自动执行权限策略。用户能否读到对象、关系、引文和派生摘要，还要由访问控制实现。[C11] [C15]

## 三、怎样应用：让同一套定义服务查询、推理、AI 与业务操作

### 先用于统一查询

产品登记库写“batch inference”，另一份手册写“批量推理”。本例可以在核实两者含义一致后，将它们关联到同一个功能概念；若“批量处理”含义更宽，就保留区别，而不是简单合并名称。

查询时先定位功能和产品版本，再匹配环境与有效时间，取回相应支持声明及证据。这种应用的收益来自统一概念、身份和条件，不要求每次都做复杂逻辑推理。跨来源数据如何统一访问，可以采用前面介绍的映射路线。[C07] [C17]

精确数量和完整清单还需知道数据是否覆盖完整。在只收集部分手册的知识库中，“查到五个版本”不能直接变成“只有五个版本支持”。

### 需要新结论时，再使用推理

假设定义了“企业版发布版本是软件发布版本的一种”，已有数据记录“产品 A 2.1 是企业版发布版本”。在相应语义下，可以推出它也是软件发布版本。这个结论来自定义和断言，不是从文字名称猜出来的。[C20]

推理还可用于检查要求范围内的逻辑问题，但必须选择支持所用公理的引擎。Jena 文档就区分了不同推理配置，并明确其内置 OWL 规则推理不是完整 OWL DL 实现。因此，“能存 OWL”与“能完成指定推理任务”要分别验收。[C21]

数据形状验证则回答另一个问题：这条支持声明有没有版本、环境和证据等必需字段？逻辑一致、结构合格、现实陈述准确，是不同检查。[C04] [C20]

### 接入 RAG，帮助大模型取到合适的证据

本例的建议流程是：先把用户问题中的产品、版本和功能解析清楚，再通过受控查询取回支持声明，回查原文，最后让大模型解释结果。

这样，Ontology 主要帮助确定“查什么、哪些关系成立、条件是什么”。数据库负责取回数据，原文提供证据，模型组织答案。上线时应比较有无概念归一和关系查询的效果，不能只凭答案更长判断本体有用。

GraphRAG 是另外一组检索策略。微软实现中的 Local 会结合图上下文与原文片段，Global 使用社区报告回答全库层面的问题。这些检索和摘要机制不等于 OWL 的形式推理。[C22] [C20]

### 接入业务应用或 Agent

如果用户进一步要求“为某产品升级创建评审单”，本体可以帮助应用明确涉及哪个产品、哪个版本、哪些声明和证据。真正提交评审单的逻辑，应由业务动作接口执行。

Palantir 的 Action Types 展示了对象模型如何连接对象、属性和关系的修改，是业务运营型 Ontology 的一个产品实例。这种动作层不应被理解为 OWL 推理器自然附带的功能。[C23]

自行实现时，本文建议动作接口检查用户权限、当前修订、参数、审批和重复提交，再执行操作并记录审计。大模型可以提出计划，不能自行授予写权限。

## 四、落到一个项目，先交付什么

如果现在要做产品知识库，我建议先选一小类产品，完成以下工作：

先写一组真实问题和答案标准，收集能回答它们的权威资料。根据资料定义产品、版本、功能和支持声明，记录名称歧义与稳定标识。再做数据库映射或文档候选抽取，保留来源和条件，完成审核。

存储路线根据问题选择：标准交换与语义查询需求明确时评估 RDF；关系浏览与路径查询是主要需求时评估属性图；已有业务库应继续管理原数据时，评估虚拟访问。不要同时引入全部路线。

接着提供一个能返回对象、条件和证据的查询接口，用真实问题验收。需要推理的题单独测试；需要自然语言解释时接入 RAG；需要改业务状态时再增加动作服务。

最后，用一次版本升级、一次资料纠错、一次权限撤销和一次来源删除检查系统是否还能正确回答。构建成功的标准，是问题能被可靠回答、知识能被维护，而不只是图里已经出现了很多节点。

本文没有启动服务、运行语义引擎或做性能复现。更细的代码示意见此前的 [贯穿示例](2026-10-23_Ontology构建到应用_贯穿示例.md)，标准进展见 [核实附录](2026-10-23_Ontology标准与方法_核实附录.md)。
