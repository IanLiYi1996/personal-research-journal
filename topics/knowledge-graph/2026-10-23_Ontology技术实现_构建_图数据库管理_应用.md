# Ontology 技术实现：构建、图数据库管理与应用

核实与测试日期：2026-10-23。

本文讲具体实现。属性图原生管理与 RDF／OWL 是两条并列路线，前者不要求先导入 OWL。使用同一个“产品版本支持某项能力”的模型，说明定义如何建立、怎样成为存储与校验规则、如何查询并接入应用。

本文给出的元模型、写入流程与接口是方案设计；标准和数据库能力以一手资料为依据。代码分为两种：本地已执行的 RDF／SHACL／OWL-RL 示例，以及尚未在数据库服务执行的 Cypher、Fuseki 配置。不要把前者的测试结果推广为后者已部署成功。

## 1. 构建的产物：先把定义写成可处理的模型

### 1.1 模型定义和具体事实分别长什么样

本例需要回答：

> 在指定时刻，哪些产品版本在 Linux 自托管环境支持批量推理？对应证据是什么？

为了回答它，定义至少有 Product、Release、Capability、SupportClaim 和 Evidence。EnterpriseRelease 是 Release 的子类。SupportClaim 记录版本、能力、环境、状态、有效时间和证据；不直接在产品节点上保存一个永久的 `supports=true`。

下面是本例的模型描述，不是 OWL 或 Neo4j 内置格式。可以把它作为模型服务的输入，生成不同技术栈所需的表达：

```json
{
  "model_version": "0.1.0",
  "entity_types": [
    "Product", "Release", "EnterpriseRelease",
    "Capability", "SupportClaim", "Evidence"
  ],
  "subclasses": [
    {"child": "EnterpriseRelease", "parent": "Release"}
  ],
  "properties": [
    {"owner": "Release", "name": "version",
     "datatype": "string", "required": true}
  ],
  "relations": [
    {"name": "FOR_RELEASE", "source": "SupportClaim",
     "target": "Release", "min_targets": 1, "max_targets": 1},
    {"name": "ASSERTS", "source": "SupportClaim",
     "target": "Capability", "min_targets": 1, "max_targets": 1},
    {"name": "SUPPORTED_BY", "source": "SupportClaim",
     "target": "Evidence", "min_targets": 1}
  ]
}
```

它能告诉程序：有哪些类型、哪些关系合法、哪些属性和连接必须存在。但保存这段 JSON，不会自动让数据库执行所有规则。需要一个明确的转换或校验过程：

- 属性图路线：生成元模型节点、可表达的数据库约束，以及关系数量等应用检查。
- RDF 路线：生成类／属性表达、SHACL 形状和数据映射；需要正式逻辑时生成并审查 OWL 公理。

不同输出的含义不能自动视为完全相同。例如必填字段适合数据校验；OWL 的存在性限制不能直接代替它。[T01] [T02]

具体事实则是另一份输入：

```json
{
  "claim_uri": "https://example.org/onto-tech/Claim21",
  "release_uri": "https://example.org/onto-tech/Release21",
  "capability_uri": "https://example.org/onto-tech/BatchInference",
  "environment": "linux-selfhosted",
  "valid_from": "2026-10-20T00:00:00+08:00",
  "evidence_uri": "https://example.org/onto-tech/Evidence21",
  "model_version": "0.1.0"
}
```

`status` 和 `tenantId` 在本例由可信审核与身份服务赋予。不能接受文档或 LLM 自行声明“已批准”或“管理员所属租户”。

### 1.2 传统技术怎么得到这些定义

人工建模从用途、能力问题、可复用词汇开始，再定义类、关系、属性和实例。Stanford 的方法允许自顶向下、自底向上或混合建立层次，并要求迭代检查；其框架式示例不是完整 OWL 公理工程规范。[T03]

传统半自动技术分别处理不同输入：

1. 规则抽取：匹配句式或标注模式。例如 GATE 的 JAPE 规则可从文本抽取关系候选。
2. 术语与层次候选：分词、词性、名词短语、词形归一和评分；TermRaider 还利用中心词提示层次。
3. 结构数据映射：从表、主键和关联表制定对象及关系映射。R2RML 定义关系数据到 RDF 的映射，允许按业务词汇定制。

前两类结果仍需判断“词是不是概念”“关系是不是事实”；第三类需要确定字段的业务含义，并非表结构自动等于正确本体。[T04] [T05] [T06]

### 1.3 当前 LLM 辅助流程的输入、输出与检查

本例建议将 LLM 处理拆为两个流程：

**模型提案**输入领域资料与真实问题，输出候选类型、定义、别名、关系和映射。提案需经过业务评审与模型版本发布，不能立即改变线上 schema。

**实例抽取**输入已经发布的模型、文档快照和片段，输出候选对象与陈述。先校验类型、关系、字段、标识和引文，再审核事实。不能让每份文档自动增加新关系类型。

具体检查顺序：

```text
解析输出
→ 类型／关系白名单和字段检查
→ 引文与原文位置检查
→ 对象身份消歧
→ 条件、单位、否定、版本核对
→ 证据是否支持陈述
→ 审核与发布
```

这些是工程建议。结构检查或引文存在检查通过，并不说明引文确实支持结论；模型自报置信度也不能直接批准事实。

OntoGPT 主要按既定模式从文本抽取并 grounding 到本体标识；预设映射模板后，也可输出 OWL 公理。Schema Automator 可从既有模式／数据生成或增强 LinkML 模型。实例抽取、模型生成和正式逻辑设计需分别验收。[T07] [T08]

## 2. 路线 A：用图数据库原生管理 Ontology

### 2.1 定义图和实例图分别保存什么

这里直接使用属性图建模，不经过 RDF 导入。Neo4j 提供节点、标签、关系、属性和 Cypher，足以保存下面的模型元数据与业务实例；这是一种工程本体管理设计，不是系统自动附带的完整 OWL 实现。[T09]

定义图包含：

```text
OntologyVersion
  CONTAINS_TYPE → EntityType
  CONTAINS_RELATION → RelationType

EntityType
  SUBCLASS_OF → EntityType
  HAS_PROPERTY → PropertyDefinition

RelationType
  FROM_TYPE → EntityType
  TO_TYPE → EntityType
```

`EntityType` 保存概念标识、定义、名称及模型版本。`PropertyDefinition` 保存数据类型、必填等要求。`RelationType` 保存方向、合法端点和数量规则。版本不同的同一概念，使用“稳定概念标识＋模型版本”区分定义记录。

实例图则保存：

```text
Release — RELEASE_OF → Product
SupportClaim — FOR_RELEASE → Release
SupportClaim — ASSERTS → Capability
SupportClaim — SUPPORTED_BY → Evidence
实例对象 — INSTANCE_OF → EntityType
```

Claim 上放 `environment`、`validFrom`、`validTo`、`status`、`modelVersion`。Evidence 保留文档快照和引用位置。它们不只是附属展示字段，而是查询、撤销与审核必需的条件。

完整原生示例在 [neo4j-model.cypher](technical-example/neo4j-model.cypher)。其中定义记录的核心片段为：

```cypher
MERGE (v:OntologyVersion {uri:'urn:onto-tech:model:0.1.0'})
MERGE (t:EntityType {
  modelVersion:'0.1.0',
  iri:'https://example.org/onto-tech/Release'
})
SET t.name='Release', t.definition='A particular product release.'
MERGE (v)-[:CONTAINS_TYPE]->(t);
```

**它只保存定义。** `PropertyDefinition.required=true` 或 `RelationType.maxTargets=1` 不会自动生成数据库约束；编译器或写入服务必须明确读取并执行规则。

### 2.2 哪些要求可以直接交给数据库

例如，唯一性可以显式创建：

```cypher
CREATE CONSTRAINT release_uri IF NOT EXISTS
FOR (r:Release) REQUIRE r.uri IS UNIQUE;

CREATE CONSTRAINT type_identity IF NOT EXISTS
FOR (t:EntityType)
REQUIRE (t.modelVersion, t.iri) IS UNIQUE;
```

Neo4j 社区版支持属性唯一性；属性存在性、属性类型和键约束属于企业版。唯一性约束不保证属性存在，类型约束也不保证必填。因此要区分 edition 与约束覆盖范围，不能只写“数据库支持 schema”。[T10]

必填版本号、Claim 只能连接一个 Release、关系不能跨模型版本等检查，见 [neo4j-validate.cypher](technical-example/neo4j-validate.cypher)。例如：

```cypher
MATCH (c:SupportClaim)
OPTIONAL MATCH (c)-[link:FOR_RELEASE]->(r:Release)
WITH c, count(link) AS targets
WHERE targets <> 1
RETURN c.uri, targets;
```

这个查询检测违规，并不自动阻止其他写入。建议由受控写入服务执行：校验输入 → 写入与检查 → 失败回滚 → 成功提交。对并发基数等要求，还需按对象串行化、锁定或乐观并发控制；仅“在同一事务检查一次”不能代替全部并发设计。

### 2.3 当前还有原生 Graph Types

这不是只能靠元模型节点的路线。Neo4j 当前文档说明，Graph Types 在企业版、Cypher 25、2026.06+ 可显式声明图 schema，并在 2026.07+ 提供把当前 graph type 作为虚拟图查看的方式。[T11] [T12]

以下是 schema 迁移示意，未在服务器执行；仅适用于满足版本／edition 条件且不会与现有定义冲突的隔离测试库：

```cypher
CYPHER 25
ALTER CURRENT GRAPH TYPE ADD {
  (:Release => {
    uri :: STRING NOT NULL,
    version :: STRING NOT NULL
  })
}
```

`ADD` 用于增加新 element，不能用来修改已存在的 element；模型发布器需要先检查当前 graph type，再生成迁移计划。`SET` 会替换之前的 graph type 或 constraints，不能把它当作安全的增量同步命令。[T32] [T33]

查看 schema 图：

```cypher
CYPHER 25
SHOW CURRENT GRAPH TYPE AS GRAPH
```

当前 Graph Types 是 open graph types：只约束声明覆盖的数据，不会自动拒绝所有未声明节点、关系和属性。如果项目要求封闭的类型白名单，还需由写入服务等明确执行。[T11]

需要区分三个东西：

- 自建定义图：概念含义、来源、版本、评审记录等业务语义。
- 原生约束／Graph Type：显式声明并由数据库执行的数据 schema。
- 推理：按指定逻辑推出结论。

保存定义图不会自动修改 Graph Type；Graph Type 也不会仅凭数据类型声明获得 OWL 的开放世界、公理蕴含等全部语义。数据库当前 schema 与多个历史模型版本的映射，还需应用维护；不能因为同时保存 v1、v2 节点，就认为原生 schema 自动按版本隔离。

### 2.4 怎样查询继承、条件与证据

元模型中保存 EnterpriseRelease→Release 后，可以显式查询：

```cypher
MATCH (target:EntityType {
  modelVersion:$modelVersion,
  iri:$targetType
})
MATCH (object)-[:INSTANCE_OF]->(actual:EntityType)
      -[:SUBCLASS_OF*0..]->(target)
WHERE object.modelVersion=$modelVersion
  AND object.tenantId=$tenantId
RETURN DISTINCT object.uri;
```

这是类层次路径匹配，适合明确受限的继承查询；不是任意 OWL 公理的推理器。另一个实现是由导入器为子类对象物化父类标签，示例的 Release21 同时有 Release、EnterpriseRelease 标签；这是导入器做的，不是 Neo4j 自动继承。[T13]

完整条件查询见 [neo4j-query.cypher](technical-example/neo4j-query.cypher)，会过滤模型版本、租户、环境、审核状态及时间，并返回 Claim、Release、Product 与 Evidence。

参数由后端绑定。`tenantId` 来自认证上下文，不能由 LLM 任意指定。这里的租户过滤只是示例，不包含对象级、字段级或跨租户共享授权的完整实现。

## 3. 路线 B：RDF 表示、OWL 公理、SHACL 校验

### 3.1 三元组和数据集具体怎么写

RDF 的对象用 IRI 标识，客体还可以是有数据类型的字面量；多个 named graphs 组成 dataset。Turtle 表达图，TriG 可表达带图名的数据集。本例用 URI 区分模型、Release、Claim 和 Evidence，避免靠显示名称做主键。[T14] [T15]

定义文件 [ontology.ttl](technical-example/ontology.ttl) 包含：

```turtle
@prefix ex:   <https://example.org/onto-tech/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .

ex:Release a owl:Class .
ex:EnterpriseRelease a owl:Class ;
    rdfs:subClassOf ex:Release .
ex:releaseOf a owl:ObjectProperty ;
    owl:inverseOf ex:hasRelease .
```

`subClassOf` 是类继承公理，`inverseOf` 是属性逆关系公理。它们比保存“有一条名叫 SUBCLASS_OF 的边”多了规定好的形式语义，但只有相应引擎或明确实现才会执行推理。[T16]

事实在 [data.trig](technical-example/data.trig) 中：

```trig
@prefix ex:  <https://example.org/onto-tech/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<urn:onto-demo:asserted:public:v1> {
  ex:Release21 a ex:EnterpriseRelease ;
      ex:releaseOf ex:ProductA ;
      ex:version "2.1" .
  ex:Claim21 a ex:SupportClaim ;
      ex:forRelease ex:Release21 ;
      ex:capability ex:BatchInference ;
      ex:environment "linux-selfhosted" ;
      ex:status "approved" ;
      ex:validFrom "2026-10-20T00:00:00+08:00"^^xsd:dateTime ;
      ex:hasEvidence ex:Evidence21 .
}
```

完整数据还包含过期、未批准、不同环境及受限图的记录。图名用于组织和选择数据，不自动成为授权规则。示例的图白名单由测试代码显式选择。

### 3.2 必填、类型、基数怎样执行

OWL 的开放世界语义不把缺失值直接判为假；存在性限制与数据图中“必须有字段”的检查不同。因此结构要求放入 [shapes.ttl](technical-example/shapes.ttl)。[T01] [T02]

```turtle
@prefix ex:  <https://example.org/onto-tech/> .
@prefix sh:  <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:ReleaseShape a sh:NodeShape ;
  sh:targetClass ex:Release ;
  sh:targetSubjectsOf ex:releaseOf ;
  sh:class ex:Release ;
  sh:property [
    sh:path ex:version ;
    sh:minCount 1 ; sh:maxCount 1 ;
    sh:datatype xsd:string ; sh:minLength 1
  ] .
```

`targetClass` 选择相关实例；`targetSubjectsOf` 还能抓到有 releaseOf 关系但类型信息不完整的对象。否则，坏数据若根本没有目标类型，可能被纯类型 target 跳过。完整形状还检查 Claim 的合法端点、证据、环境和状态枚举，以及 `validTo > validFrom`。

校验参数固定为：

```python
validate(
    data_graph=authorized_view,
    shacl_graph=shapes,
    inference="none",
    meta_shacl=True,
    inplace=False,
)
```

本例把模型图和获准事实图组成 data graph，先在明确配置下校验，再推理。SHACL 的类检查可利用子类关系，但这不等于执行完整 RDFS／OWL 推理。是否先推理再校验，会改变一些结果，应作为版本化配置。[T02] [T17]

例如，缺失类型可能被 domain 公理推导补齐。若应用要求来源明确声明类型，先推理再校验就可能掩盖缺失；若应用接受推导类型，则应另定义规则。不要由库默认设置决定业务语义。

### 3.3 推理怎样运行，范围是什么

本地参考代码使用：

```python
DeductiveClosure(
    OWLRL_Semantics,
    axiomatic_triples=False,
    datatype_axioms=False,
).expand(view)
```

使用 owlrl 的 OWL-RL 规则扩展，示例验证两项：

```text
Release21 type EnterpriseRelease
EnterpriseRelease subClassOf Release
→ Release21 type Release

Release21 releaseOf ProductA
releaseOf inverseOf hasRelease
→ ProductA hasRelease Release21
```

这是具体库、具体配置、具体公理的测试，不是任意 OWL 2 DL／Full 的完备性证明。EL、QL、RL 是限制表达以服务不同任务的语言片段；需要更多表达能力时，要检查目标推理器实际覆盖范围。[T18] [T19]

原始断言与推理视图应分开。本文示例复制获准图后计算扩展，不把所有新增三元组回写来源图。撤销依据后，最小实现可重新计算对应视图；生产系统再按规模评估增量依赖追踪。

### 3.4 SPARQL 如何处理时间、环境和证据

完整 [query.rq](technical-example/query.rq) 使用变量绑定：

```sparql
PREFIX ex: <https://example.org/onto-tech/>
SELECT DISTINCT ?claim ?release ?version ?evidence ?quote
WHERE {
  ?claim a ex:SupportClaim ;
      ex:forRelease ?release ;
      ex:capability ?capability ;
      ex:environment ?environment ;
      ex:status "approved" ;
      ex:validFrom ?from ;
      ex:hasEvidence ?evidence .
  ?release a ex:Release ; ex:version ?version .
  ?evidence ex:quote ?quote .
  OPTIONAL { ?claim ex:validTo ?to . }
  FILTER (?from <= ?at)
  FILTER (!BOUND(?to) || ?at < ?to)
}
```

`capability`、`environment`、`at` 由后端绑定。先限制可见图，再计算推理和查询，不能先用全部数据生成答案然后只过滤引用。

在本例中，Release21 原始数据只有 EnterpriseRelease 类型。未经推理的直接 `a ex:Release` 查询没有当前记录；OWL-RL 扩展后返回一条。也可以显式把类型查询改为：

```sparql
?release rdf:type/rdfs:subClassOf* ex:Release .
```

本地两种方式都测过。后一种只是类路径匹配，不等于执行逆关系、等价类等其他公理。[T20]

## 4. 持久存储和查询服务怎么接

### 4.1 Neo4j 原生部署需要哪些组件

最小组件是数据库、受控模型／数据写入服务和查询 API。原生元模型方案无需 APOC 或 n10s。需要标准 RDF 导入或有限层次推断时，可以另评估 n10s；它的局部能力不等于完整 OWL 推理。[T09] [T21]

建议在隔离环境先导入：

1. `neo4j-model.cypher` 的唯一性约束；
2. 模型版本与定义记录；
3. 明确版本、租户和证据的实例；
4. 参数化查询与检测违规的查询。

定义同步不是直接 `MERGE name`。应以稳定 IRI／URI 和模型版本定位对象；如果概念定义变化，生成新定义版本并记录迁移。Demo 中的 SET 是固定样例初始化，不是生产同步算法。

数据库层持久化、备份、连接池与监控按所选部署配置。本文未选择商业部署方式或测算费用，也未在 Neo4j 服务运行这些脚本。

### 4.2 RDF 持久存储：Fuseki＋TDB2

配置文件 [fuseki-config.ttl](technical-example/fuseki-config.ttl) 将查询服务绑定到磁盘 dataset，而不是只创建一个内存 Graph：

```turtle
@prefix fuseki: <http://jena.apache.org/fuseki#> .
@prefix tdb2: <http://jena.apache.org/2016/tdb#> .

<#service> a fuseki:Service ;
  fuseki:name "onto-demo" ;
  fuseki:serviceQuery "sparql" ;
  fuseki:serviceUpdate "update" ;
  fuseki:serviceReadWriteGraphStore "data" ;
  fuseki:dataset <#store> .
<#store> a tdb2:DatasetTDB2 ;
  tdb2:location "/var/lib/fuseki/onto-demo-data" .
```

完整配置包含 server/service 列表。磁盘路径是专用目录占位示例，实际部署需配置所有权、备份及读写权限。TDB2 负责持久化，Fuseki 提供端点；这两步并不自动配置完整 OWL 推理。[T22]

按该 service 名与 endpoint 配置，路径是：

```text
/onto-demo/sparql    查询
/onto-demo/update    SPARQL Update
/onto-demo/data      Graph Store HTTP
```

以下命令未执行，只展示已启动、受保护的本地测试服务如何接入文件：

```bash
curl -X POST \
  'http://127.0.0.1:3030/onto-demo/data?graph=urn%3Aonto-demo%3Amodel%3A0.1.0' \
  -H 'Content-Type: text/turtle' \
  --data-binary @ontology.ttl

curl -X POST \
  'http://127.0.0.1:3030/onto-demo/data' \
  -H 'Content-Type: application/trig' \
  --data-binary @data.trig
```

Graph Store POST 合并目标图，PUT 会替换目标图；向支持 quad 扩展的 dataset 端点 POST TriG，按其中图名接入。生产操作必须解析精确目标、验证输入并实施授权，不能把 PUT 用成“随便增量更新”。[T23] [T24]

Named graphs 不应被假定自动合入默认图。跨图查询要显式选择数据：

```sparql
PREFIX ex:   <https://example.org/onto-tech/>
PREFIX rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT DISTINCT ?release
WHERE {
  GRAPH <urn:onto-demo:asserted:public:v1> {
    ?release rdf:type ?class .
  }
  GRAPH <urn:onto-demo:model:0.1.0> {
    ?class rdfs:subClassOf* ex:Release .
  }
}
```

这是显式查询模型图和事实图，不要求服务器已运行完整 OWL 推理。若要 Jena InfModel 或预物化推理视图，需要单独配置基础图、reasoner 和权限范围；默认图包装的推理示例不能直接推广为所有 named graph 已启用同样语义。[T25]

### 4.3 保留原 SQL 数据：Ontop

虚拟知识图的配置至少包含数据库连接、映射和可选 ontology。示意 OBDA 映射：

```text
mappingId ReleaseMapping
target <https://example.org/release/{release_id}> a ex:Release ;
       ex:version {version} ;
       ex:releaseOf <https://example.org/product/{product_id}> .
source SELECT release_id, product_id, version FROM product_release
```

这是格式示意，未在 Ontop 执行；还需正式的 prefix／mapping 文件结构、连接与标识规则。目标是 RDF 模板，来源是 SQL，查询按映射改写到源库执行。Ontop 定位于 RDFS／OWL 2 QL 的轻量语义，不应视为任意 OWL 的完整推理器。[T26]

这样本体与映射可以单独管理，数据由原 SQL 系统负责；代价是源库负载、查询改写、跨来源能力与权限传播要实测。不是所有项目都必须增加一个物理图数据库。

## 5. 版本、更新、校验与删除怎样成为管理流程

以下是本文提出的生产设计要求，不是数据库已经全部自动提供的功能。

### 5.1 发布模型版本

模型发布包包含：

```text
模型定义／元模型快照
约束或 Graph Type 迁移计划
SHACL／应用校验版本
源数据映射版本
查询模板与接口版本
推理引擎及配置
问题测试与负例
变更、迁移和回滚说明
```

持久化的定义版本可以并存；当前数据库 schema、应用选择的模型版本与事实所属版本则需要明确映射。稳定标识和可取回的发布版本可借鉴 OBO 的版本原则，但不把社区要求当作全领域强制标准。[T27]

### 5.2 写入和纠错

建议写入服务执行：

```text
可信认证上下文
→ 绑定已发布模型
→ 校验字段、身份和引用
→ 检查合法端点与关系数量
→ 检查审核状态转移及并发修订
→ 提交来源断言与审计
→ 重建受影响索引／推理／摘要
```

`candidate → approved → revoked` 的状态转移由审核服务控制。业务新版本与模型新版本分开：Release 2.2 不必改变 Ontology 0.1.0；修改 `SupportClaim` 的含义却可能需要模型迁移。

来源记录建议保留文档哈希／快照、片段定位、引用、处理程序版本与审核活动。PROV-O 可表达来源链，但不会自动验证陈述真实。[T28]

### 5.3 撤销依据和删除派生内容

若 Evidence21 被撤销，先判断 Claim21 是否还有其他有效证据；不能一律删除同名事实，也不能继续引用已失效证据。

受影响项应包括：

- 原始陈述状态；
- 推理或便捷边；
- 全文／向量索引；
- 实体摘要、社区报告与回答缓存；
- 尚未执行的动作计划。

最小参考实现通过重新计算获准图的 OWL-RL 扩展处理撤销；生产增量实现需要依赖与支持来源追踪。只有有向边而没有依据记录，很难精确撤销。

权限变化与事实变化分别处理。即使某事实仍然真实，也不意味着原用户还可读取它。Graph 名、Tenant 字段和本体类继承不应自动赋予权限。

## 6. 应用如何调用：结构化查询、RAG、Agent

### 6.1 先给应用稳定接口

两种存储路线都可以暴露同一业务接口，内部使用不同查询：

```text
POST /v1/support-claims/search

{
  "capability_uri": "https://example.org/onto-tech/BatchInference",
  "environment": "linux-selfhosted",
  "at": "2026-10-23T10:00:00+08:00",
  "model_version": "0.1.0"
}
```

接口名与数据结构为本文设计示意，未启动 API。用户身份和租户由认证上下文绑定。

返回至少包括 Claim、Release、Product、条件、证据、模型版本和数据更新时间。明确返回“来源断言”还是“推理结果”；未知、冲突与无权限不得统一写成“不支持”。

### 6.2 查询结果怎样进入 RAG

建议步骤是对象解析 → 参数与权限检查 → 静态查询模板 → 证据回查 → 上下文组织 → 生成 → 引用支持检查。

Ontology 在这里提供概念、身份和合法关系；数据库执行查询；原文提供依据；模型解释结果。普通文档检索、关系扩展和社区归纳需要按题型评测。Microsoft GraphRAG 的 Local／Global／DRIFT／Basic 是检索方式，不是 OWL 推理器。[T29]

LLM 不应直接决定动态标签、图名或关系类型并拼接查询。若确需生成查询，应执行解析、读写分类、模板／标识白名单、授权与资源上限检查。参数绑定解决值的拼接问题，不自动解决全部授权问题。

### 6.3 动作怎样执行

模型可以提出 `propose_release_upgrade`，实际动作服务检查：

```text
对象与模型版本
用户权限
参数与业务前置条件
expected_revision
审批要求
idempotency_key
执行、审计及恢复
```

这些是建议的动作控制项。Palantir 的 Action Types 是对象模型连接业务修改的一个产品实例；对象定义或逻辑推理不会自行授权调用者写入。[T30]

外部证据文本属于不可信输入。OWASP 指出 RAG 不能完全防止提示注入；高风险工具调用应采用最小权限和必要的人类审批。[T31]

## 7. 已验证什么，未验证什么

### 7.1 本地执行结果

环境：Python 3.14.5，RDFLib 7.6.0、pySHACL 0.40.1、owlrl 7.6.2；依赖只安装在本次临时环境，没有修改系统 Python。完整代码与固定版本在 [technical-example](technical-example/README.md)。

执行：

```text
verify.py
13 tests run
0 failures
0 errors
SHACL conforms: true
authorized view: 86 triples
OWL-RL expanded view: 330 triples
current query result: Claim21 / Release21 / Evidence21
```

测试覆盖缺证据、缺版本、错误数据类型、错误时间区间、缺类型时不被 target 跳过、类继承、逆关系、查询与推理／路径的区别、时间／环境／状态过滤、撤销、受限图排除及 named graphs 保留。

这里的图白名单是固定 fixture，不是完整多租户安全系统；测试通过不说明已证明不存在所有信息泄露。

Fuseki 配置的 Turtle 语法也已本地解析；没有启动 Fuseki、TDB2 或 Neo4j。Cypher、Graph Types DDL、HTTP 导入与 Ontop 映射仅经过文档核对，未在相应服务执行。

### 7.2 不同路线到底承诺什么

| 要求 | 原生属性图路线 | RDF／OWL 路线 |
|---|---|---|
| 存定义与历史版本 | 自建版本化元模型，必要时连接原生 schema | 保存本体图、版本、形状和映射 |
| 保证字段和结构 | 可用的数据库约束＋应用检查；Graph Types 有 edition／版本条件 | SHACL／数据库及应用规则 |
| 类继承查询 | 明确 Cypher 路径或导入器物化 | 类路径或所选推理配置 |
| 复杂逻辑蕴含 | 另加明确的规则／推理服务，不从标签自动获得 | 选择实际覆盖所需公理的引擎 |
| 来源、时间、权限 | Claim／Evidence 与控制服务 | 陈述／证据图与控制服务 |
| 对接 RAG／Agent | 稳定业务 API 与受控 Cypher | 稳定业务 API 与受控 SPARQL |

如果项目主要是对象管理、依赖与业务查询，可以从原生属性图和受控元模型开始。确有正式语义交换或逻辑任务，再选择 RDF／OWL 或加入映射。这是方案建议，不是产品性能排名。
