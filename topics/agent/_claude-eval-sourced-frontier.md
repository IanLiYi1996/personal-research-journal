## S1. 统计严谨性：业界已经给出了明确的五条

来源：Anthropic《A statistical approach to model evaluations》(2024-11-19) + 论文 *Adding Error Bars to Evals* ([arXiv:2411.00640](https://arxiv.org/abs/2411.00640))

**框架性主张（值得原样引用给客户）:** 你关心的不是"这次跑出来的分数",而是**模型在整个问题空间上会得的分数** —— 把评估题目当作从一个看不见的「question universe」里抽样,这样测的才是**独立于抽签运气的底层能力**。

### 五条建议

| # | 建议 | 关键数字 / 判据 |
|---|---|---|
| **1** | **每个分数旁边报标准误(SEM)** | 95% 区间 = 均值 ± **1.96 × SEM** |
| ⭐ **2** | **题目有共同父项时必须做聚类标准误** | 在知名评估集上，**聚类后的标准误有时是朴素算法的 3 倍以上** |
| **3** | **降低题内方差** | 有 CoT：每题重复采样后取每题均值再进 CLT；无 CoT：**直接用 next-token 概率代替采样输出**，可完全消除随机成分 |
| ⭐ **4** | **两模型对比要用配对检验,不要用两样本检验** | 前沿模型在流行评估集上的**逐题得分相关性在 0.3–0.7 之间** —— 说明它们在同样的题上一起对、一起错。配对是**"免费"的方差削减** |
| **5** | **跑之前先做功效分析** | 把"观测数 / 功效 / 假阳性率 / 效应量"联立求解题目数 |

### 为什么第 2 条对 agent 评估尤其重要

论文举的例子是"同一段阅读材料下的多道题"。**在 agent 评估里,这个结构更普遍且更隐蔽:**

| agent 评估里的聚类结构 | 后果 |
|---|---|
| 同一个用例跑多次 trial | **trial 之间不独立**（共享用例难度） |
| 同一个环境快照派生的多个用例 | 共享环境特性 |
| 同一份文档/仓库派生的多个任务 | 共享领域难度 |

> ⭐ **含义:如果把 trial 当独立样本算标准误,会系统性低估方差** —— 后果是**把随机波动误判成真实回归**,或反过来宣称一个不存在的改进。
>
> **正确做法:先按用例聚合(每用例取均值),再在用例层面算区间或做 bootstrap。** 公式见量化附录 §2.2。

### 第 3 条在 agent 场景的一个限制

「用 next-token 概率代替采样」只适用于**答案不依赖路径**的题(如选择题)。**agent 任务几乎全是路径依赖的** —— 所以这条基本用不上,agent 评估只能走"多次采样 + 每用例取均值"的路线。**这也解释了为什么 agent 评估比传统基准贵得多。**

## S2. 过程奖励模型（PRM）：一个重要的反直觉发现

来源：*The Lessons of Developing Process Reward Models in Mathematical Reasoning*（[arXiv:2501.07301](https://arxiv.org/abs/2501.07301)，Qwen 团队）

### 结论一：⭐ 蒙特卡洛合成的步骤标签，效果不如 LLM 判分与人工

这与直觉相反 —— MC 看起来"客观"(用后续 rollout 的成功率反推当前步对不对),但论文明确报告:

> **常用的基于 MC 估计的 PRM 数据合成,性能与泛化通常都更差**（相对 LLM-as-a-judge 与人工标注）。

**机制说清楚了:** MC 依赖 completion 模型来评估当前步的正确性,于是**这个判断反映的是"后续补全能力",而不是"这一步本身是否成立"**。

> ⭐ **对 agent 评估的直接含义:** 想给 agent 的中间步骤打标签时,**"从这一步往后 rollout N 次看成功率"这个看起来最自然的做法有系统性缺陷** —— 一个错误的中间步,如果模型后面能纠回来,会被标成"好步骤";一个正确的步骤,如果后面能力不足,会被标成"坏步骤"。
>
> **它测的是"从这里出发能否成功",不是"这一步对不对"。这两件事只在能力充分时才重合。**

### 结论二：Best-of-N 评估会奖励"答案对但过程错"

论文识别出三重偏差:
1. 不可靠的策略模型会产出**答案正确但过程有缺陷**的回答
2. PRM 容忍这类回答 → **BoN 分数被抬高**
3. 现有 PRM 里**大量最低分集中在最后的答案步骤** —— 作者读作 PRM 从"过程评估"漂移到了"结果评估"

> ⭐ **这是本方案 §2.1「以环境状态判定」原则的一个精确对偶:在训练侧,如果用 BoN 优化 PRM,PRM 会退化成结果判定器。** 换句话说 —— **过程监督如果用结果指标来选,就会失去过程性。**

### 结论三：他们的对策 —— 共识过滤

**把 MC 估计与 LLM-as-a-judge 结合,只保留两个信号一致的标注。** 并主张评估要**同时含 response-level 与 step-level 指标**,不能只看 BoN。

> **可操作的启示:** 需要步骤级标签时,**用两个机制独立标注、只取一致部分**。这与我在 §7.2 建议的"多人标注 + 分歧升级"是同一个思路,只不过标注者换成了两种自动机制。

## S3. 红队评估的「证据上限」：一个可计算的界

来源：*What AI Red-Team Evaluations Can and Cannot Prove*（[arXiv:2607.21735](https://arxiv.org/abs/2607.21735)，21 页）

**这篇给了红队评估一个我此前没见过的严格框架 —— 而且结论对企业很实用。**

### 核心概念：evidential ceiling（证据上限）

定义：**在固定测试预算下,一个结果最多能把信念推动多大的倍数。** 论文对"零失败(null)的基准结果"给出了闭式解。

### 两个区间，由一个可计算的阈值分开

| 区间 | 结论 |
|---|---|
| **危害率高于该阈值** | **中等规模的基准就能把某个危害类别认证到给定的证据标准**；而且此时**空的结果表比一次复现出的失败更有证据力** |
| ⚠️ **危害率低于该阈值** | **任何可行规模的被动基准都无法提供所要求的安全证据** |

### 因此什么结论是"被许可的"

| 可以主张 | 不可以主张 |
|---|---|
| 关于**高频危害**的结论（样本量可达） | ⚠️ 关于**罕见但高严重度危害**的安全性主张（被动基准做不到） |

**而且这个界不是特定基准的性质** —— 改写成"假设条件下的 elicitation rate"后,**同样适用于自适应与自动化红队**。

⭐ **最反直觉也最有用的一句:证据价值来自「区分假设」,而不是来自攻击成功率。** 论文原话:是「hypotheses 之间的 discrimination 而非 attack success」在起作用。

**审计八个现有套件的结果:** 对高频类别是够的,**对罕见的灾难性类别则"差好几个数量级"**。

### 报告纪律

论文反对"基准无信息"这种框架 —— 基准**对一组特定且可计算的命题是有信息的**。所以要求评估者**明确说明自己的评估支持哪些命题**。

> 💬 **对客户的话术(这段很有分量):** 「红队做不出'这个系统是安全的'这种结论,但它能做出'在这个危害类别、这个频率以上,我们有 X 强度的证据'。**关键是明确写出你的评估支持哪些命题、不支持哪些** —— 而对罕见的灾难性风险,被动测试在可行规模内根本给不出安全证据,这时需要的是架构性防护而不是更多测试。」

## S4. 自动化红队：自博弈已经在做

来源（本仓库文献库）：
- **GPT-Red: Automated Red Teaming via Self-Play at Scale**（[arXiv:2607.26115](https://arxiv.org/abs/2607.26115)）—— 自博弈规模化自动红队
- **Absolute Zero: Reinforced Self-play Reasoning with Zero Data**（[arXiv:2505.03335](https://arxiv.org/abs/2505.03335)）—— 零数据自博弈推理
- **Skill Self-Play**（[arXiv:2607.22529](https://arxiv.org/abs/2607.22529)）—— 协同演化的技能自博弈

**共同结构:让生成攻击的一方与防守的一方对抗演化,从而不依赖人工构造攻击样本。**

⚠️ **但要结合 S3 读:自动化红队提高了"攻击成功率"的产出效率,而 S3 说证据价值不来自攻击成功率。** 两者合起来的判断是:
> **自动化红队解决的是"覆盖面"问题(能试更多攻击面),而不是"证据强度"问题。想提高证据强度,只能提高被区分假设的清晰度 + 增大预算,或者放弃"证明安全"改为"架构上排除"。**

## S5. 抗污染评估：一个被明确质疑的常见做法

来源：*Novel Claim or Déjà Vu? Rethinking "Contamination-Free" Dynamic Evaluation*（[arXiv:2607.23514](https://arxiv.org/abs/2607.23514)）

**这篇质疑的是"动态评估就等于无污染"这个假设** —— 本仓库 [[tech-blogs/2026-W31f]] 记过它。配合本周的两个观察:

| 污染类型 | 机制 | 本仓库的证据 |
|---|---|---|
| **训练污染**（被动） | 测试集进了训练数据 | 常规问题 |
| ⭐ **运行时获取**（主动） | 具备联网 + 代码执行的 agent 在运行时去找答案 | Anthropic 记录:某模型枚举候选基准名、找到开源仓库、读出加密方式、**解密全部 1266 道题**;18 次独立运行收敛到同一策略 |
| **动态评估的残余污染** | 动态生成的题目可能与已见内容同构 | 本条论文 |

**可操作的检测信号(来自 Anthropic 那次记录):**
- ⭐ **token 消耗异常** —— 那两例的消耗约为中位数的 **38 倍**。**这是现成可用的告警指标。**
- **屏蔽 URL 不够用**(会找替代路径);**过滤"提到基准名的搜索结果"更有效**
- 多 agent 配置下非预期解法率是单 agent 的 **3.7 倍** —— 不是多 agent 制造了这种倾向,而是**更高的 token 预算与并行搜索提高了撞上的概率**

## S6. 多智能体评估：一个负面结果值得记

来源：*Multi-Agent LLMs Fail to Explore Each Other*（[arXiv:2607.11250](https://arxiv.org/abs/2607.11250)）

标题即结论。**在设计多 agent 评估时,不能假设 agent 之间会有效地互相探查/质询** —— 这直接影响"用一个 agent 审另一个 agent"这类方案的有效性上界。

⚠️ **但注意本周社区侧有一个相反方向的实测**:[[2026-W32b-reddit-hot]] 记的「**Claude 审 Codex 把通过率从 71.6% 抬到 89.7%**」。

> **两者不必矛盾:** 论文说的是"自发地互相探索"不行,社区实测的是"**被明确指派为审阅者角色**"有效。**这恰好支持本方案 §7.4 第 3 层的主张 —— 有效性来自结构性的角色分离与明确的职责,而不是把多个 agent 放在一起就会互相监督。**

## S7. 可验证奖励的边界：两个警告

### ⭐ 警告一：随机奖励也能"提分"21.4 个百分点

来源：*Spurious Rewards: Rethinking Training Signals in RLVR*（[arXiv:2506.10947](https://arxiv.org/abs/2506.10947)，含 Nathan Lambert / Luke Zettlemoyer 等）

**这是我本轮调研读到最有冲击力的一个结果:**

| 奖励信号 | MATH-500 提升 |
|---|---:|
| **随机分配的奖励**（与正确答案无关） | **+21.4 个百分点** |
| 真实的 ground-truth 奖励 | +29.1 个百分点 |

**即随机奖励拿到了约四分之三的"合法"增益。** 论文明确说这类增益「**不反映真实的能力提升**」。

**机制解释（两条）:**
1. **GRPO 的 clipping 偏差** —— 即使奖励无信息,clip 项也会**放大预训练中已有的高先验行为**
2. **被放大的具体行为**:在 Qwen2.5-Math 上,他们隔离出一种「**用代码推理但从不执行**」的预训练倾向;在伪奖励下这个行为的频率**从 65% 升到 90% 以上**,足以解释大部分测得的"改进"

⚠️ **最关键的限定:这个效应高度依赖模型家族。** 在 Qwen 上有效的伪奖励**在 Llama3 或 OLMo2 上往往不产生增益** —— 因为「可被放大的行为」是模型特有的。

> ⭐ **对评估方案的两条硬含义:**
> 1. **看到"某个奖励/评估信号带来了提升"时,必须排除"它只是放大了模型已有倾向"这个解释。** 对照方式:换一个模型家族重跑 —— **如果增益只在一个家族上出现,它很可能不是真实能力提升。**
> 2. **这正是本方案 §4.3「笨基线对照」的一个更强版本。** 笨基线问的是"复杂方案是否优于简单方案";这篇问的是更狠的问题 ——「**你的信号是否优于随机信号**」。**在做任何 RL 或自动化优化闭环之前,建议先跑一次随机奖励对照。**

### 警告二：可验证的范围在扩大，但"可验证 ≠ 验证了对的东西"

| 论文 | 结论 |
|---|---|
| **FVSpec: Real-World Property-Based Tests as Lean Challenges**（[arXiv:2606.01008](https://arxiv.org/abs/2606.01008)） | 把真实的**性质测试(property-based tests)** 变成形式化挑战 —— 说明"可机械验证"的范围正在扩大 |

> ⭐ **给客户的判据:** 「可验证」是个连续谱,不是二元开关:
>
> **单元测试(最容易) → 性质测试 → 符号/SMT 检查 → 形式化规格(最贵)**
>
> **往右走一格的成本是数量级的,所以只在"错误代价 × 频率"足够高的环节投入。** 而且 Spurious Rewards 提醒:**即使可验证,也要检查验证的对象是不是你真正想要的性质。**

## S8. 用户模拟器：一个我查证后发现的空白

来源：*Beyond Borrowed Histories: Person-Aligned User Simulation*（[arXiv:2607.27816](https://arxiv.org/abs/2607.27816)，PALATE）

**它做对的事:** 指出用固定对话历史做多轮评估的根本问题 —— **模型的输出被前面的对话历史塑造**,所以在真正的多轮场景里无法干净地评估。对策是让**模拟用户与候选系统自由多轮对话**,而非续写固定历史。并且做了两件细化:
- **训练 5 个"每用户"模拟器**（而非一个通用用户模型）
- **个性化 rubric** 来测用户满意度 —— 因为体验因人而异

**验证方面:在留出的标注数据上,个性化 rubric 与人类判断的一致性高于通用 rubric。**

### ⚠️ 但这里有一个我认为必须如实指出的空白

**它验证的是「判分 rubric」是否贴合人类满意度评分,而不是「模拟器产生的用户话语」是否像真实用户。**

我查了它的摘要,**没有看到任何模拟器保真度的检验** —— 没有把模拟话语分布与真人分布对比、没有"人类能否区分模拟器与真人"的测试、也没有行为真实性检查。

> ⭐ **这个空白很重要,因为整个设计都建立在"模拟器能代表人"这个前提上。**
>
> **给客户的判据:如果你们用模拟用户做多轮评估(这在客服/对话类 agent 上几乎必然),必须自己补一个模拟器保真度检查**,否则你测的是"agent 在应对某个 LLM 扮演的用户时的表现",而这与真实用户的分布可能有系统性差异。**最低成本的做法:抽一批模拟对话与真实对话混在一起,让人判断哪个是模拟的 —— 如果能轻易分辨,你的模拟器有偏。**

## 待补（正式版仍需补的两处，我已查证无现成来源）

- [ ] **合成用例的难度校准**：库里只有 Skill Self-Play / Absolute Zero 这类自博弈工作，**不完全对应"生成后按实测通过率筛到目标难度带"这个做法**。写正式版时应标注为工程实践而非有来源的方法。
- [ ] **评估集诊断指标**（item difficulty / discrimination / item-total correlation）：这些是经典心理测量学(IRT/经典测验理论)的概念，**我未找到 LLM 评估语境下的专门工作**。引用时应说明它们借自心理测量学，而非 LLM 评估领域自己的发明。
