## TL;DR

**核心主张**：**每隔约半年，把你的 `CLAUDE.md`、skills、hooks 全部删掉重写**——因为它们是为**上一代模型**写的脚手架，新模型不再需要，甚至会被拖累。对 Opus 5，Cherny 的建议更激进：**"真心建议大家试试把这些东西全删掉，因为模型已经不需要了。"**

实证依据是 Claude Code 自身：配合 Claude 5 系列（Opus 5 / Fable 5），其**系统提示被砍掉 80%+**，如今 harness 里"几乎只剩下**安全、权限和静态分析**的部分"。

方法论上他给了一个可操作的工具：**ablation study（消融实验）**——把系统提示整段删掉，再**逐行加回**，看每一行到底起什么作用。

## 三个概念

### 1. Unhobbling（解缚）—— "解开缰绳"的实际含义

不是"少写提示词"这么简单，而是三件具体的事：

| 做法 | 具体说明 |
|---|---|
| **给更难的任务** | 给模型你认为它做不到的任务；只说清**目标、边界、退出条件**，然后放手 |
| **多做实验** | 包括没有明确商业目的的、好玩的实验 |
| **让模型自我验证** | 他认为**瓶颈已不是 prompt engineering，而是如何让 Claude 在任务中途验证自己的输出**——没有自我验证，就无法长时间自主运行。他说这是当前大家做得最差的一环 |

态度上：**放弃控制欲、把模型当同事、别过度指定、别强迫它按你的方式工作**——因为"模型不是那样工作的"。

### 2. Product Overhang（产品悬余）

模型能力**跳跃式**提升，而产品集成是**渐进式**的，于是能力长期超出产品所暴露的部分。

**他给的例子**：2024 年底的 Sonnet 3.5 已经能一次写完整个文件，而当时 Copilot 和早期 Cursor 还在做**自动补全**。Claude Code 给出完整终端访问权限，部分弥合了这个落差。

### 3. Model Elicitation（模型激发）

内部有人把 **Opus 5 接上 OpenCV**，发现它**能画肖像、动物、风景**——尽管从未被训练过画画。能力是通过**提示 / 上下文 / 工具 / 产品形态**浮现的，**权重没有任何改变**。

> 转述里提到一个有意思的归因争议:这是"激发出潜在能力"还是"脚手架教会了新技能"?**Cherny 认为这个区分不重要**,他只看到"巨大的机会"。

## 最生动的案例：跑了 14–15 天还没停的任务

他的 prompt 大意是：**把一个 Electron 应用重写成 Swift；在 Mac VM 里运行 Electron 版、截图，与 Swift 版逐像素对比；不达标就别停。**

被问跑了多久时——**还在跑，大约 14–15 天**。而且 Claude 自己**建了一个内部 Slack 频道，每隔几分钟发一张进度截图**——转述者形容它决定"直播"。

这个案例把前面三个概念串起来了：给足够难的任务（unhobbling）、说清退出条件、让它自己验证（逐像素对比就是自我验证机制）。

## 我的反思

### A. 这与我此前的判断互为印证，但把时间尺度钉死了

我在 [长程 agent 研究路径整理](/research-notes/2026-07-20-long-horizon-agents.md) 里记过一条判断：**"harness 里显式实现的能力，后续会被内化进模型策略"**，并说"判断一项 harness 技术的长期价值，要看它能否被内化"。

Cherny 的说法是同一件事的**实践版**,而且更狠——他不只说"会被内化",而是给出**运维节奏:半年一次清空重写**。这把一个抽象判断变成了可执行的日程。

### B. 但"全删"这个建议要打个折扣

值得注意的是,量子位自己链接了一篇更早的文章,标题暗示 **Opus 5 又把删掉的提示词加回去了一部分**（"Claude Code狂删80%提示词，Opus 5反手加回去了"）。这说明:

- **"砍 80%" 不是单调过程**,而是删了再补的**震荡收敛**;
- 留下来的是"安全、权限、静态分析"——**这三类恰恰是模型学不会/不该学的**（涉及外部系统状态与不可逾越的边界）。这正好印证我在长程 agent 笔记里的那条 Open Question:**"哪些能力必须留在 harness"** ——答案初见端倪:**安全护栏留下,能力性脚手架删掉**。

### C. "评测比 harness 更耐用"是本篇最被低估的一句

他顺带提到:**evals 比 harness 和 prompt 更持久,但模型进步太快会让 eval 套件饱和**,所以要观察模型仍然卡住的地方、在那里设计新 eval。

这条与本周 Reddit 的 "benchmaxx 条件反射"、以及 HF Papers 的"评测转向测失效模式"**三源共振**——**行业正在从"测能力上限"转向"找失效边界"**。

### D. 一个我不完全认同的点

"放弃控制欲、把模型当同事"在**能力评估**上成立,但在**生产环境的可审计性**上是有代价的:一个跑了 15 天、自己开 Slack 频道汇报的 agent,若中途走偏,**回溯成本极高**。Cherny 的语境是前沿实验室的探索性使用;搬到有合规要求的生产系统里,"解开缰绳"需要配套的**可观测性与中止机制**——这一点转述里没有讨论。

## Open Questions

1. **"半年"这个数字有依据吗?** 转述里没有给出机制解释,它更像经验法则(跟模型代际节奏挂钩)。如果模型发布节奏变快,这个周期会不会缩短到季度?
2. **删掉 harness 后能力真的不掉吗?** 需要的是 A/B 数据(同任务、同模型、有/无 harness),而访谈只给了定性主张。这正是他自己推荐的 ablation study 该产出的东西——**但公开的数据没有**。
3. **"安全/权限/静态分析"留下**是因为模型学不会,还是因为**不该让模型自己决定**?这两个理由对应完全不同的长期走向。
4. 自我验证是新瓶颈——那**谁来验证验证器**?模型自评的可靠性上限,与本项目 [推理努力度综述](/research-notes/2026-07-20-blog-reasoning-effort.md) 里"LLM 尚不能可靠自我纠错"的文献结论存在张力。
